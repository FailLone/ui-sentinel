## 确认与未知

- 确认：两例的元素与规则摘要通常已在每次输入中，继续增加规则检索工具并不能自动解决重复调用。C2 的原始错误分页和 C5 的离散观察是具体开销来源。
- 确认：C2 的 ref 从 s6 到 s7/s8 更新，历史窗口也发生裁剪；部分重新读取有定位/记忆原因，不能全部删除。当前持久规则摘要能避免规则事实完全消失，但没有阻止重新检索。
- 确认：模型多工具调用已存在，并非每个工具一定消耗独立模型往返。
- 未知：供应商排队、推理和生成分别占多久；无法由 reasoning token 比例解答。也不能断言改清楚输入就必然更快。
- 未知：Agent 是否会接受结构化汇总、从而减少重复确认，还是新增摘要反而增加输入和推理负担。需要同输入重放。

#### 失败的具体含义

1. **当前执行器 C2：决策输出耗尽。** 已保存 supported 指针拦截发现，后台零订单。第 5、6 次请求均在 4096 输出 token 上限结束，返回 `length`；一次安全恢复后仍不能给出完整动作，最终 `model-stream-incomplete:length`。HTTP 成功不等于 Agent 决策成功，也不能把六次调用很少理解成已优化到极致。
2. **Browser Use C2：同类决策收敛失败。** 规则证据已保存、零订单，但第 5 次请求耗尽输出上限且 content 为空，原生 structured-output 解析失败，没有主动完成。不是网络等待了 300 秒，也不是检查工具未接通。
3. **Stagehand C2：发现成立，恢复路径超出冻结 oracle。** 它保存了拦截证据，反复点击后通过 Tab/Enter 完成一笔支付，再以 observed-blocker 主动结束。C2 原 evaluator 要求零订单和 unknown 业务结果，因此失败。实验没有明确禁止普通键盘恢复，不能将这个失败写成“没有发现遮罩”或“强制点击违规”；它暴露了 evaluator 将鼠标阻断与业务不可完成绑定的局限。保留原评分，不事后改规则抬高通过率。若未来评价恢复能力，应先明确普通键盘恢复的允许范围，并将 UX 缺陷与业务最终结果分开定义。
4. **Browser Use C5：测量语义错配。** 它发现并登记重试假设，但先做多次离散等待，随后选择 `element-visible` 和 1000ms；实际六个样本都为 true。它仍试图提交“五秒内不可操作”的 supported 结论，被共同证据守卫拒绝，保留 open 假设并以执行错误结束。不能用看起来正确的自然语言报告替代正确测量。原生配置在一次失败后停止；这是本次受测配置的结果，不证明框架不能配置其他恢复策略。

当前执行器和 Stagehand 的 C5 则分别有 31 个样本 / 至少六秒、26 个样本 / 5010ms 的连续 actionability 测量，最大样本间隔均 206ms、全部 false，关联对应假设与禁用按钮；后台各一笔 failed 订单，并主动结束。结论仅覆盖实际测量窗口，不外推无限时间或任意更早的时间段。

Stagehand C0 的 13 个原生步骤实际产生 18 次上游请求；`act` 的嵌套定位和最终结构化输出都计费。Browser Use C5 还曾把 `quality_inspect` 当作 `extract` 查询，产生额外模型调用；完整网关记账捕获了这些请求。少数公开 API 调用不能代表内部工作更少。

本批没有发现需要使用修正额度的接线缺陷。输出上限、错误测量选择、未达评分口径属于真实受测结果，不以改提示词、增加预算、放宽 oracle 后重跑来覆盖失败。默认执行器保持不变，但这只是没有候选合格的保留决定，不是现架构最优的证明。
