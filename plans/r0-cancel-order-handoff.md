## 唯一顺序判定及窗口为何关闭

同一个 run 的启动认领（含配置/契约失败等提前终态）、取消受理、最终提交，都先取得 queue 的 `withRunLifecycle` 串行仲裁。仲裁在读取状态之前取得，并覆盖异步持久化。外部 API 的预读不能授予受理权。

取消先进入：在仲裁中确认当前仍可取消，持久化唯一的 `run:cancel-requested`，标记已受理并中止活动执行，再返回 true。重复并发取消共用已有请求，不重复落事件。后续 `commitRun` 读取这一标记，选择 cancelled；原 `finish:accepted` 保留为已经发生的结束意图，但其证明不再获得有效完成结论。

终态先进入：`commitRun` 设置一次性的 terminal ownership，确定最终停止原因，持有同一个仲裁直至全部终态/统计写入和独立持久校验完成，或真实失败隔离结束。等待中的取消不能穿越 SQL / await 窗口，取得仲裁后返回 false，API附拒绝原因；第二个终态意图也被拒绝。终态提交失败仍保持所有权和隔离，不把它伪装为取消成功。

真实未知写入优先于已受理取消；退出清理后再次以真实 sideEffectPending 提出 reconciliation-required，原业务隔离不撤销。关闭响应提交、浏览器清理、abort signal 和既有 model-attempt guard 仍约束迟到操作；启动前增设 guard 防止已受理取消后还新建浏览器。终态提交及持久校验的异常统一保留 storage-inconsistent 与队列隔离。

这是现有单进程、串行执行服务内的顺序协议，不宣称跨进程分布式锁，也没有把多步终态记录变成一个数据库事务。进程在提交中崩溃或数据库失效时，仍由原重启/持久一致性规则保守处理，不能把已受理取消等同于保证取消已完成。本轮重启验证针对已经完成持久提交的记录。
