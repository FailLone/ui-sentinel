## 为什么前次修复没有覆盖

本轮的业务/UI 请求追踪分离解决了“被拒的 POST 被当成真实未知写入”；末尾取消检查解决了浏览器清理期间已经到达的取消。现有 B18 在动作执行期间调用取消，没有在最终检查后、异步状态写入前受理取消。因此两者都没有建立取消 API 与终态提交之间的原子顺序。

flush/seal 修订解决“决策落库”和“未完成只读请求”的生命周期混用，也不会自动给 run 的终态提交加锁。再加一次 `isCancellationRequested` 检查仍然留下下一个 await 的窗口；放宽历史验证或把错误改成 partial 只会掩盖矛盾。当前历史验证和 K3 scorer 拒绝本反例是正确行为，不能移除该拒绝。

可推翻本判断的证据应证明原 SQL 窗口无法真实并发受理取消，或钩子改变了取消/提交语义，而非仅调整时序。已核对钩子原样转发 SQL、API 正式受理、持久事件顺序及零写入事实，当前证据支持上述根因。

## 下一次受限修复的共同契约和最小验证路径

以下是修复建议，**本轮尚未实施**，不把新标准追溯覆盖旧失败。

1. 取消受理和终态提交须由同一个 per-run 仲裁入口决定顺序；不能各自读取状态后独立写入。推荐将它收敛到 queue / run-manager 的运行生命周期边界，再由 executor 提交终态意图，避免继续在主执行器增加检查点。仲裁持有期间覆盖取消事件持久化、终态选择及一致提交；不得在接受取消后让旧完成意图覆盖它。
2. 顺序边界前受理的取消：无真实未知写入时最终 cancelled，已发生的 finish 事件保留为历史意图，不能继续当作有效完成证明；取消与旧事件存在本身不应制造存储不一致。顺序边界后取消：返回未受理，不再追加 accepted cancellation 事件。正在等待仲裁的请求必须重核状态，不能使用等待前的 getRun 快照。
3. 已派发且未知的业务写入始终保持 reconciliation-required 的优先级，即使取消已受理。真实持久化失败/半提交仍触发原隔离；不得为了下一正常任务通行而统一清除隔离或跳过完整性校验。崩溃重启仍需按持久事实处理，进程内仲裁不能替代持久提交协议。
4. 最小 A 验证：确定性屏障覆盖取消先取得顺序、提交先取得顺序、多个取消并发、取消读到旧状态后等待、提交持久化失败、真实未知写入和取消竞争；断言事件、API受理结果、终态以及历史证明含义一致。不要靠随机多跑碰概率。
5. 最小 B 验证：沿用本次正式 API / 实际浏览器与相同调度屏障，边界前取消应 cancelled 且下一干净任务完整完成；边界后取消应未受理且原终态/证明有效；真实未知业务写入仍隔离下一任务；重启与数据库独立读取一致。保留原 B18、健康完整完成和旧 C10 拒绝标准。
6. 先提交这一原子顺序的实现方案及定向证据，再判断是否需要扩大免费回归；不得自动进入整批付费重跑。修复和免费反例全部闭合后，再由另一 Agent 复核新候选资格。
