# 执行关键路径与并行调研

日期：2026-09-23。研究对象：本地 `main` / `32974a7` 与已完成的冻结对照批次。此次仅阅读代码、重算既有记录和查阅官方资料，没有调用付费模型、改动运行代码或重新进行验收。

结论：优先缩短收尾决策，再验证独立证据分析的并行。当前没有证据支持更换 Mastra，或让多个 Agent 同时操纵同一页面。下列方案是待验证提案，不是已经取得的性能收益。

## 2. 调用依赖与当前实现

代码定位：

- `src/execution/executor.ts`：模块级 tail 串行执行 Run；每个 Run 的 serial/toolTail 串行工具；外层 while 等待 executeModelRequest 完成再开始下一轮。
- `src/execution/model-request.ts`：Mastra generate，maxSteps=1；一次请求可产生多个工具，maxSteps=1 不等于只能调用一个工具。当前 executor 最多允许一次决策八个工具，但会排队执行。
- `src/execution/vision.ts` 与 executor 的 aiLocate 调用：Qwen 是操作定位后备，不是后台视觉巡检。候选 34 次请求全部为 Agent 请求，视觉调用为零。
- `src/execution/task-state.ts`、run_finish：已有假设、触发分支、待检查规则和收尾核验；不能把不存在的通用任务完成账本描述为现成能力。
- `src/execution/profiling.ts`：已有嵌套与重叠 wall time 口径，尚无完整的业务依赖图和模型流式里程碑。

典型暖路径是：

```text
Agent：选择商品操作
  → 执行动作与采集
Agent：选择已验证导航片段
  → 逐步导航与采集
Agent：提交订单
  → 等待业务响应与采集
Agent：语义绑定规则与目标
  → 完整五秒测量、判定与证据保存
Agent：生成结束决策和总结
  → run_finish 重新核验、持久化
```

这些节点大多消费前一步新产生的事实，不能简单 Promise.all。五秒测量也不能与同一页面的滚动、跳转、关闭遮罩或写操作重叠，否则改变了被测过程。可以同时处理此前已经冻结、且不需要操作页面的证据。

当前六轮规则计算合计不足 0.2s，即使假设把这部分完全消除，也只约占 350.7s 的 0.06%。非模型部分中又有约 30.6s 的规则测量；不能为速度缩短声明要求的五秒窗口。

整组 85 次请求均未启用 stream。网关的 firstByteMs 实际在 fetch 获得响应头时记录，不是首个模型 token，不能用它区分排队、prefill、推理和输出生成。此次无法追溯真实 TTFT 或 token 间空闲时长。

## 3. 外部方案及其适用边界

均于研究当日查阅官方文档；网页版本可能领先本项目锁定版本。并行能力也检查了本地 Mastra 类型声明，包含 workflow.parallel、foreach concurrency、toolCallConcurrency。

| 方案 | 可借鉴能力 | 对本项目的判断 |
| --- | --- | --- |
| [Mastra Control flow](https://mastra.ai/docs/workflows/control-flow) | parallel、分支和受限并发 | 现有栈可承载并行。parallel 要等所有分支结束才继续；后台分析跨多个页面动作运行，需要任务队列、版本绑定和汇合点，不能仅包一个 parallel。 |
| [LangGraph Workflows and agents](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents) | 独立子任务并行、orchestrator-worker | 是相同调度思想的另一种实现，没有证据表明迁移能缩短现有模型推理。 |
| [Browser Use 参数](https://docs.browser-use.com/open-source/customize/agent/all-parameters) | flash_mode 精简决策字段、单轮多动作、页面变化停止动作批次 | 借鉴短决策与有边界的动作批次；不照搬重试默认值，不为快而取消必要的未知问题探索。 |
| [Stagehand 速度优化](https://docs.stagehand.dev/v3/best-practices/speed-optimization) | observe 的动作结果可直接交给 act，减少再次模型推断 | 与我们导航片段复用方向一致。其文档的示例速度不是本项目收益；为加速而移除媒体、动画的建议不适用于体验巡检，可能掩盖缺陷。 |
| [Midscene 缓存](https://www.midscenejs.com/caching) | 缓存规划与定位，失效后回到模型；不缓存 query/assert 结论 | 复用如何到达和如何定位；新的页面与操作仍需新证据，不能复用旧 pass 掩盖回归。 |
| [Playwright Authentication](https://playwright.dev/docs/auth) | 复用登录状态，写服务端状态时隔离账号 | browser context 隔离不等于购物车/订单隔离。单账号写操作需资源锁，不因新建页面就视为安全并行。 |

OpenRouter 的 [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection) 支持按 latency/throughput 选择供应商，适合作为单独实验变量；原有固定供应商代码对照不能混入路由变更。其 [Streaming](https://openrouter.ai/docs/api/reference/streaming) 文档指出心跳不是模型内容、流中可能报错，取消推理与计费还取决于供应商。不能把“收到 SSE”当作取得有效进展，也不能保证客户端 abort 后不计费。

### 3.1 具体借鉴与接入决定

上一版表格仅列能力，未充分区分“直接使用库”“借鉴实现”和“我们自己的扩展”。补充检查 Browser Use 当日 main 源码后，明确如下。远端 main 是浮动版本，真正引入依赖或移植代码前应固定提交并检查许可证；此次没有复制实现代码。

**A. 优先借鉴 Browser Use 的精简输出协议，而不是引入另一套 Agent。**

其 [AgentOutput.type_with_custom_actions_flash_mode](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/views.py) 在输出 schema 中删除 thinking、evaluation_previous_goal、next_goal 和计划字段，仅要求 memory/action。关键是减少协议要求模型生成的内容，不只是提示“请简短”。这不等于关闭供应商模型内部推理；对 DeepSeek reasoning token 的效果必须单独测量。

本项目已经使用工具调用，不需要再套 memory/action envelope。适配位置是 executor 中的 Agent 指令、run_finish 输入 schema 与报告组织：结束只提交必要的短理由/证据引用，结果分类由服务器核验，报告复用已持久化事实；探索仍可提交新假设。先验证这个小改动，避免同时改模型、路由、历史和结束状态机。我们的“条件式结束意图”是额外设计，不是 Browser Use 的现成功能。

**B. 借鉴 Browser Use 的动作批次中断机制，扩展已有 journey，而非并发点击。**

其 [Agent.multi_act](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/service.py) 逐个执行同次决策的动作，通过动作的 terminates_sequence 标记以及执行前后的 URL/页面焦点目标变化中断剩余动作，发生错误或完成也停止。源码还明确阻止将 done 作为后续批次动作，不能据此声称它支持“检查与结束一起盲执行”。

我们可在现有 `execution/journeys/runner.ts` 基础上研究短动作批次，用当前元素引用与逐步前后条件验证；发生新遮挡、目标变化、导航或未知副作用立即交回 Agent。已有 journey 已经部分体现这种思想，不能再次计为全新收益。冷启动同页面表单填写是未来适用场景，本次暖导航样本的收益可能有限。新增批次工具并非本轮首要改动。

**C. 借鉴 Stagehand 的“定位结果可执行”，避免模型套模型。**

[observe 文档](https://docs.stagehand.dev/v3/basics/observe) 展示将返回的动作对象直接传给 act，避免执行阶段再做一次模型推断。本项目保留 Playwright 执行，在目标绑定阶段产出受约束的动作描述（目标引用、页面版本、允许动作、前置条件），执行层校验后直接操作；视觉模型也只返回定位/证据，不再启动第二个自主操作循环。当前 elementRef、aiLocate 后备和 journey 已部分实现。暂不把 Stagehand 从实验依赖升级为生产执行器，也不直接采用任意脚本执行接口。

**D. 直接使用已有 Mastra 的并行编排，资源约束仍由本项目提供。**

本地安装版本已经有 `.parallel()`、`.foreach()` 并发设置与 `toolCallConcurrency`。可直接用于同一不可变证据包的独立分析任务；但 SDK 的工具并发不会绕过 executor 的 serial，也不能代替页面锁、账号资源锁、预算预留、证据版本与收尾汇合。先拆出不访问 Page 的证据分析服务，再接 Mastra 编排；跨动作后台任务需单独登记生命周期，不能每一步都等待全部分析。

**E. 采用 Midscene 的缓存边界，暂缓新增定位缓存。**

[缓存文档](https://www.midscenejs.com/caching) 区分可复用规划/定位与不缓存的 query/assert 结果。我们维持当前严格事实版本下的规则结果复用，不将旧页面结论迁移到新状态；若后续视觉定位请求足够多，再验证 Midscene 定位缓存的接入和失效。当前对照没有视觉调用，这项无法改善已观测瓶颈。

落地分类：A 是下一步优先做的协议适配；D 是后续并行实验直接使用的库能力；B/C 是现有机制的进一步完善；E 是保留边界并暂缓扩展。LangGraph 作为设计参照，不新增依赖。没有任何一个已查方案能替我们定义业务检查完成条件或自动提供同账号业务状态隔离。

## 4. 建议先做：收尾协议与请求测量

### 4.1 补齐分段时延

为每个请求记录角色/用途、attempt/retry、输入输出与缓存 token、供应商、请求开始、响应头、首个有效模型增量、首个可用工具调用、结束、取消传播。工具参数必须完整解析并通过校验才执行，不能边收到半段 JSON 边操作页面。

保留整体截止时间。后续如加入首有效增量/空闲超时，需要用观测分布确定阈值；心跳不能重置进展计时。重试继续遵守“未开始工具且没有不确定副作用”，所有尝试计入预算与费用。暂不做双请求竞速。

流式首先是诊断手段，不承诺提升端到端速度，也不自动缩短模型生成量。协议改变单独验证，再固定到两组共同测量设施，避免混淆传输与决策优化。

### 4.2 将结束决定与长篇总结分开

第一步维持 Agent 主动结束：明确结束工具只需要短理由或证据引用；业务结果、已保存发现、覆盖情况由执行层基于事实核验和组织报告。不要再要求模型复制完整报告、重复生成结果分类。输出限长必须显式且经契约测试验证，不能把截断的工具 JSON 当成完成。

Agent 仍可选择继续探索、报告阻断或提交结束意图。不能仅因已知规则全部 pass 或 hypothesis 列表为空就自动认为页面没有未知问题。现有 taskState 只知道已经登记的范围，不知道尚未发现的问题。

如果短结束决策仍占主要时间，再单独试验“条件式结束意图”：Agent 在最后一次检查前明确声明预期收尾条件，执行层在检查后验证范围版本、所有任务终态、结果是否 unknown、有无新异常、页面变化与待核验发现，满足才接受该意图；否则返回 Agent。不能将 rule_check 和 run_finish 当成两个无依赖工具一起盲目发出。

条件式结束是新工具协议；验收必须显式识别 Agent 的授权意图和服务端接受事件，保留阻断/未知与主动结束的语义，不把后台强制截止伪装成 Agent 主动完成，也不重写旧 M5 成绩。第一步短结束实验不需要这个扩展。

结构化报告应同步可用；可选自然语言润色可异步生成，并标明尚在生成。最终报告就绪时间仍需记录，不能通过把报告搬到后台隐瞒总体耗时。

## 5. 再做：冻结证据的并行分析

建议保持单一页面操作者：Agent 动态探索、决定下一步；执行层负责采集、调度与副作用边界。语义绑定、未知异常发现仍由模型完成。

```text
页面操作者 → 动作 → 一致性校验后的不可变证据包
                       ├─ 确定性检查
                       ├─ 按需 Qwen 视觉检查
                       └─ 按需业务语义复核
                                  ↓
                       带证据版本的结果收件箱
                                  ↓
                  下一决策边界消费 / 请求现场验证 / 收尾汇合
```

这项同时新增视觉发现能力，不能拿“没有视觉检查的旧版”对比“并行视觉的新版”来宣称并行提速。正确比较是相同检查任务和触发策略下的串行与并行。

最低契约：

- 每项任务包含 runId、taskId、parentTaskId、dependsOn、snapshotId/factVersion、operationId、输入证据引用、deadline、预算预留和取消信号。
- 声明资源：冻结证据只读、当前页面观察/操作、账号或业务实体写权限。不依赖 HTTP method 推断全部业务副作用。
- 初始只允许一个页面操作者和一个后台模型分析任务同时运行；共用 Run 的调用/费用预算，以原子方式预留。此并发值是保守实验起点，不是最优值证明。
- 结果描述原始快照里的现象；页面已变化时，不能直接使用旧坐标点击。需要现场验证的候选进入待办，操作者在合适时机重新绑定和验证。
- 测量窗口内对相关页面/资源持有锁；独立快照分析可以并行，修改被测条件的动作不可以。
- 发布新的快照不自动丢弃旧分析：瞬时遮挡可能正是应保留的缺陷。仅对明确可替代的任务合并；使用队列上限与背压，避免每次 DOM 变化创建一个模型任务。
- 必需检查结束前不能宣布完整报告完成；超时/取消显式记为 unverified。新异常需要现场验证时先保存原始证据，并在下一安全边界交给操作者。
- 业务写操作前等待声明为其前置条件的分析；其他分析可继续。不要每个动作后都等待所有后台任务，形成另一种全串行。

同账号多个 Run、不同只读页面的并行主要改善吞吐，未必缩短一条下单路径。当前模块级 Run 队列、全局 reconciliation 标志、私有网关单 active run 等都以串行为前提；不能简单移除 tail。跨 Run 并发与账号租约应另立范围，本轮不做。

## 6. 验证顺序与停止条件

1. 保存本次分解结果。为短结束协议、流式增量/usage/取消、迟到结果、共享预算、过期快照、测量锁和收尾汇合准备可控测试。无付费调用。
2. 先在相同冻结收尾输入上离线重放原协议与短协议，不执行真实工具或业务写操作，覆盖六个不同输入。这只能验证决策/工具参数正确性与请求时延，不能替代端到端验收。真正开跑前固定模型、供应商、顺序、样本数、预算和质量判据。
3. 短结束通过后，单独跑端到端固定对照：目标仍为总耗时改善、请求/token/成本受控、证据质量不降；保留全部超时和失败、区分冷/暖导航复用。核心指标增加最后必要检查完成到结束接受的时间，不以其中位数代替总时间门槛。
4. 并行部分先做录制轨迹与可控延迟实验，确认重叠窗口、锁和汇合正确；再以相同视觉检查任务对比串行/并行，测首次发现、检查完成、最终报告时间、召回/误报、总请求/token/费用及迟到结果。
5. 只有小规模质量和性能门槛通过，才扩大正式验收。若收尾缩短但总体不改善，检查模型服务与串行依赖；若并行没有足够独立工作或增加漏报，则保留串行，不通过扩预算或删慢样本取得好结果。

建议优先级：请求分段测量与短收尾 → 同任务端到端验证 → 按需视觉能力及其串并行对照 → 多账号/多 Run 吞吐。当前不建议更换框架、全面多 Agent 化，或并发操作同一页面。
