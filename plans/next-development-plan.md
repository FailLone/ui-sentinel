# 下一步：明确业务契约，验证第二个完整业务

状态：待开始。前置为本轮代码整理通过回归。沿用当前架构，不继续模型/框架速度矩阵，不以性能最优作为开工条件。

## 目标与范围

当前已证明购物范围的探索、发现、收尾及学习闭环。下一步证明同一执行器能够使用明确的业务要求检查第二个完整业务，而不是继续把购物经验写进通用执行器。

交付可版本化的项目/业务配置，以及一个“导出任务失败后恢复”的完整场景。保留同一 Agent、工具、原子调查、证据和结束门槛。不新增分布式、同账号并行写、向量库、PRD/Figma 自动解析或后台视觉分析。

## P1：列清现有业务假设

审查 src/agent/policy.ts、执行器中的购买/订单/重试推断、网络副作用拦截、业务终态和路径库。形成对照表：当前假设、通用执行约束、购物适配逻辑、迁移后的归属。

特别区分“最多创建一笔订单”与“所有写请求最多一次”；重试、上传分片等业务不能继承购物限制。没有适配器的响应不得根据相似字段猜为购物成功。

验收：每个购物特定分支有明确归属；从当前测试识别回归门槛；不改私有评估答案来配合抽取。

## P2：最小业务配置与适配边界

增加有 schema 和版本的配置，包含公开目标/要求、允许操作、业务副作用策略、成功/预期拒绝/unknown 判定来源。任务持久化使用的版本，使报告能够说明按什么要求检查。

通用执行器只消费规范化事实和策略；购物适配器解释现有公开页面/网络事实。保留取消、预算、未知写隔离、证据干预来源与可靠完成保护。

不允许 Agent 注入任意可执行源码，业务配置不得包含私有 case 编号或答案。无法判定的业务结果返回 unknown，不能用通用提示词补猜测。同一任务执行中不静默切换要求版本。

验收：现有购物确定性与集成回归通过；无配置、无效配置、未知结果、目标歧义和不确定写入均有明确结果。证明同一执行器没有按场景名字硬编码分流。

## P3：第二个完整业务与正反例

建设可重置的导出任务业务：发起导出 → 等待反馈 → 成功，或合理拒绝，或失败后恢复。它需有真实业务状态/公开反馈，不能只是换一个按钮名称的静态页面。

至少包含正常成功、可恢复失败、恢复入口持续不可操作、合理拒绝、操作名称/布局变化。私有评分器验证任务数量、最终状态和证据；只向 Agent 提供普通业务目标及公开要求，不提示缺陷所在。

采用现有通用重试规则验证语义迁移；如现有声明适用范围不足，提出修订并走原人工批准流程，不能偷偷扩大已批准范围。首次无规则发现与已批准规则复查分别评估。

验收：真值能独立证明各变体，重置受保护；健康/合理失败不误报，实际缺陷有完整测量与证据；未知结果不重放副作用。靶场的公开内容不泄露变体答案。

## P4：冻结后做有限真实验收

先通过格式、类型、测试、构建和本地预检，再冻结提交与构建。先第二业务五例各一次诊断；修复后用同一冻结版本各三次正式验证。稳定后运行原 minimum 固定 18 轮，确认未破坏购物闭环。

记录全部运行及失败、业务结果、发现、证据、终结原因、请求次数、usage 和时间。费用上限沿用现有验证网关；超预算或持久记录不一致则停止并保留结果，不通过放宽预算假装修复。

放行条件：第二业务 15/15、原 minimum 18/18；无误报、额外副作用或证据缺失，均按各分支明确结束。该数字是本阶段有限样本门槛，不是泛化概率保证。模型噪声导致失败也应分析，不删除失败重跑凑分。
