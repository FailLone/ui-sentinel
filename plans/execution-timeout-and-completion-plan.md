# 模型请求超时与任务收尾计划

日期：2026-09-22。基线：`e2750ad`。状态：待实施，本次只交付计划。

目标：模型请求停滞时及时终止；Agent 在约定检查范围内完成探索后能明确收尾；失败保留真实状态与证据，不以提前结束提高通过率。

关联：[执行层设计](../docs/execution-engine.md)、[最小验证计划](./minimum-validation-plan.md)、[当前进度](./minimum-validation-progress.md)、[历史实验与修复结果](./browser-loop-experiment-results.md)。

## 1. 已知问题与调查边界

用户报告两类现象：不积极调用 `run_finish`，以及第一次调用卡到整轮 300 秒。尚未取得这次运行的完整轨迹，不能把具体原因预先认定为模型推理或网络故障。

当前代码提供了可确认的工程线索：

- `src/execution/executor.ts` 的 `agent.generate()` 只传入整轮 AbortSignal，没有独立模型请求期限；`maxSteps: 1` 也会执行工具，因此一次 generate 并不等同于一次纯模型请求。
- `serial()` 内工具有独立超时，但它不能覆盖工具执行前的模型等待。
- `run_finish` 的提醒主要是提示词中的 `When done call run_finish`，没有显式收尾阶段。每轮输入有次数余额，缺少剩余时间与完成条件状态。
- 现有 `progress-classifier.ts` 按工具名分类，不能证明实际进展。调用失败的工具、重复假设或重复观察，不能因工具名不同就记作有效推进。
- 最近历史已保留动作参数和结果，旧记录可通过 `history_read` 检索；本次不恢复全量页面上下文，也不推翻已有修复。

实施先定位可用失败 Run，区分等待模型、工具执行、持久化与终态收尾。没有对应 Run 时用明确标识的故障注入复现，不编造现场根因。

## 2. 范围和约束

保留 Mastra、Playwright、Midscene 和单活动任务架构。优先补可靠性与工具契约，不迁移框架，不加入每轮额外的“裁判模型”，不扩大模型调用或总时限。

必须继续满足：

1. 业务成功、检查覆盖、缺陷判定、执行状态分别记录。订单支付成功不等于 UI 检查完成。
2. 系统可强制停止，但不能把强制停止转换为成功；既有 findings 和证据不能被收尾覆盖。
3. 页面数据属于不可信输入。完成条件来自用户目标和公开要求，不读取私有案例编号或答案。
4. 未知写结果优先进入 `reconciliation-required`，禁止重放下单、支付等操作。
5. 失败、超时、重试、unknown 用量和未覆盖项完整留档；不保存隐藏思维链。
6. 所有新增机制都有配置快照与停止原因，可以从运行报告解释为何发生。

## 3. P1：分开请求、工具和任务期限

### 3.1 配置

新增配置并做启动校验，写入 `.env.example`、README 和运行开始事件。以下是本轮初始值，必须在真实复验前冻结，调整需另起批次记录：

| 配置 | 初始值 | 作用 |
| --- | --- | --- |
| `MODEL_REQUEST_TIMEOUT_MS` | 60000 | 每个实际模型请求从发出到完整响应的最长时间 |
| `MODEL_STREAM_IDLE_TIMEOUT_MS` | 25000 | 流式调用收到首个有效数据块之后的无数据期限；非流式不启用 |
| `MODEL_REQUEST_MAX_RETRIES` | 1 | 同一逻辑决策最多一次受控重试 |
| 现有单工具期限 | 保持当前值 | 浏览器执行、视觉定位和测量仍受工具期限约束 |
| 现有整轮期限 | 保持当前值 | 所有请求、退避、工具和收尾共享，不因重试延长 |

有效期限取适用的请求、工具、任务剩余期限的最小值。当前视觉定位发生在工具内，默认工具期限短于模型请求期限时，以工具期限为准，不暗中延长工具预算。

### 3.2 实现要求

先核对已安装 Mastra/AI SDK 的类型、请求钩子和 AbortSignal 传递，用 SDK 契约测试确认实际行为，再选择最小接入点：

- 请求计时覆盖响应体读取，不能收到 HTTP headers 就清除计时器。请求没有任何数据时由请求总期限兜底，流式心跳不能无限延长总期限。
- 不把整个 `generate()` 中的浏览器执行时间混记为纯模型耗时；为模型请求和工具执行分别建立 span。
- 若 SDK 无法暴露请求边界，在 provider/transport 适配层统一实现，不靠假设某个 SDK 参数生效。主模型及 Midscene 实际请求都要覆盖。
- 每次尝试使用独立取消控制器，与整轮取消组合；请求超时不直接取消整轮控制器，以便决定是否允许安全重试。
- 超时应同时中止本地传输并使该尝试失效。只用 `Promise.race()` 返回错误而放任旧任务继续执行不合格。
- 为尝试分配不可混淆的 attempt ID。工具入口、排队执行时及产生副作用前，检查调用所属尝试是否仍有效；不能只检查“当前尝试”这个可被重试覆盖的全局变量。
- SDK 无法把工具调用绑定到具体尝试时，禁止在同一 Run 内重试；记录限制并安全结束，不放行迟到工具。
- 本地 abort 不等于供应商未计算或未收费。无法取得 usage 时保留 unknown。

### 3.3 重试判定

只允许对可重试的网络错误、暂时服务错误或请求超时重试；取消、鉴权/配置/模型协议错误不重试。认证失败和不支持的 tool 参数直接记录错误。

第一次实现采用保守条件：本次尝试未执行任何工具，尝试已失效，且没有未决写操作，才允许重试。同一尝试一旦开始执行工具，即使报错发生在 generate 返回前，也不得重放这次生成。

SDK、provider、网关内部自动重试保持关闭，只保留这一层受控重试。每次实际发出请求均计入次数预算并记录 usage；重试前检查时间与次数余额，不为重试重置任务或刷新预算。退避初始 1000ms，必须可被取消且不能越过任务 deadline。

## 4. P2：让用户和复盘程序看见执行阶段

沿用持久事件与 SSE，不另建日志系统。至少补齐：

| 事件 | 必需字段 |
| --- | --- |
| `model:request-started` | requestId、attemptId、purpose、model、startedAt、deadlineAt、retryOf（如有） |
| `model:response-started` | requestId、首个有效响应数据到达时间；接入不支持时明确 unavailable |
| `model:request-finished` | requestId、success/error/timeout/cancelled、durationMs、usage 或 unknown、错误类别 |
| `tool:started` / `tool:finished` | attemptId、toolCallId、工具名、开始/结束、结果状态、actionId（如有） |
| `run:phase-changed` | 前后阶段、触发原因、剩余时间和调用数 |
| `run:no-progress` | 连续轮数、判断依据、豁免窗口（如有） |

工具的内部 `observe()` 也属于工具 span，不能表现为模型等待。保存终态要幂等，迟到 usage/finish 回调不能重复记账、重开任务或覆盖已确定的失败。

工作台显示“等待模型响应 / 执行工具 / 验证 / 收尾”和当前阶段经过时间、deadline；模型没有响应时也能立即看见请求已经发出。错误至少区分模型超时、工具超时、整体预算耗尽和未知副作用。不把原始 prompt、密钥或供应商完整响应直接放入 UI。

## 5. P3：任务状态与收尾协议

### 5.1 精简任务状态

在现有 Run 事件/状态体系中维护可序列化的任务账本，每轮自动提供小型摘要，详情通过现有历史或按需工具检索。最小字段：

- `phase`: `exploring | verifying | finalizing`。
- 本次范围内的目标、完成条件及其 `pending | verified | unverified` 状态。
- 当前业务结果及证据引用，开放假设、必要测量与各自期限。
- 不能覆盖的分支及原因，最近有事实支持的进展。
- `timeRemainingMs`、`modelCallsRemaining`、`actionsRemaining`、收尾触发原因。

目标列表有大小上限，重复更新合并；长文字和完整页面仍存证据层。可以扩展现有 `exploration_update` 传递结构化目标/待办状态，但 Agent 的声明不能自行把事实标为已验证；服务端要校验证据归属及所需条件。不能只靠每轮追加自由文本 notes 代替状态。

最小版本不建设通用 PRD 解析器。由现有公开业务要求和当前任务目标明确本轮检查范围，Agent 在范围内发现和验证疑点；未触达的条件如实保留。不能将“支付成功”等固定购物判断推广为所有任务的完成条件。

### 5.2 阶段迁移

- 初始 `exploring`：探索本次范围，创建可验证的假设。
- 有待验证疑点时 `verifying`：执行必要测量、验证或反驳；有依据时可回到范围内探索。
- 满足完成条件，或可继续路径均已说明阻断，进入 `finalizing`。
- 即使尚未满足完成条件，剩余时间不超过 `min(60000ms, 整轮预算的20%)`，或模型请求余额不超过 2 次，也进入 `finalizing`，并标记“资源不足”，不宣称覆盖完成。
- 无进展策略也可触发 `finalizing`。同一次运行进入收尾后不重新开放探索；有新疑点则保留为未验证项。

收尾阶段既缩减暴露给模型的工具，也在服务端检查调用阶段，避免旧工具调用绕过限制：

- 允许读已有历史/证据、提交或更新既有假设的结论、保存未覆盖项、`run_finish`。
- 可补一次当前页观察，或完成一个已登记且剩余预算足够的必要测量；不能反复刷新，也不能新开无限等待窗口。
- 禁止新购物、支付、导航分支和无关假设。预算不足以完成必要测量时标记未验证，不能缩短采样却宣称已证明。
- 收尾最多消耗 2 次新模型请求，包含重试，且受整轮剩余预算限制。用完仍未结束则由系统生成部分报告并停止。

### 5.3 `run_finish` 契约

保留当前 UI/业务事实核验并复用到收尾，不以模型口头“完成”替代证据。新增结构化结束说明：已完成目标、未验证目标和原因、未解决假设；优先由任务账本生成，避免让模型复制大段数据。

本轮必需完成条件仍未满足时，不能仅凭 `businessResult=success` 接受为 `goal-reached`；明确阻断或未完成的结束请求可以保存并停止，但报告和执行状态必须如实反映缺项。目标由本次约定范围决定，不要求穷尽整个网站。

调用被拒绝时返回机器可读的拒绝原因与缺失事实，不仅抛出自然语言异常。记录 `finish-requested / finish-rejected / finish-accepted`，进展统计只有 accepted 才算成功结束。缺失事实可在收尾预算内补齐，否则系统停止为部分完成。

业务结果一旦有证据验证即可单独保存，不必等待 `run_finish`；之后若出现与该目标相关的新业务结果则重新核对。即使最终模型超时，仍可记录“业务已成功，但检查执行未完成”。这不能改变评估器对完整运行的通过条件。

新增 StopReason（不新增 RunStatus）：

| 场景 | status | stopReason |
| --- | --- | --- |
| 模型请求超时，不能/不再重试 | execution-error | model-request-timeout |
| 因无进展收尾且未被有效 finish 接受 | blocked | no-progress |
| 其他收尾机会用尽但任务总预算未耗尽 | blocked | finish-incomplete |
| 整轮时间或次数耗尽 | timed-out | budget-exhausted |
| 有效结束且满足当前完成校验 | 沿用现有映射 | goal-reached 或 blocked |

取消和 `reconciliation-required` 的既有语义优先保留。更新共享类型、API/schema、报告、UI 和评估映射；旧报告可读，新失败原因不能被当作 pass。partial 是报告描述，不新增一个未经全链路支持的数据库状态。

## 6. P4：语义上的无进展保护

保留现有分类器用于统计，新增基于事实的进展判定，不直接把分类计数当熔断条件。

初始阈值：连续 3 个完成的决策轮没有进展，给一次结构化提醒；再连续 2 轮无进展则进入收尾。新增事实或有效调查推进重置计数；重试等待、日志写入不计决策轮。

可以算进展：目标验证状态变化、相关页面/命中事实变化、对新事实的有界取证、假设获得证据支持或被反驳、有效发现被接受、必要测量向固定截止时间推进。

不能单独算进展：新截图 ID、时间戳、新请求 ID、换个说法、重复注册相同假设、调用失败的 page_act、重复读取相同历史、重复提交相同发现。不要用模型自述“我有进展”绕过计数。

有明确依据的异步反馈等待或测量窗口在期限内豁免，记录原因与截止时间；重复重建相同窗口不能延长豁免。C5 必需的 5 秒观察、正常延迟反馈和有限证据检索不能被机械地当成空转。

2. P2 事件、统计、工作台阶段展示：执行层、`src/shared/types.ts`、server/report 与 `src/web`。确认运行中能看见 start，失败后能对账。
3. P3 任务账本、收尾、完成拒绝说明：新增独立小模块，避免继续把所有逻辑塞进 executor；补共享 schema 和终态映射。
4. P4 无进展保护：新增有事实依据的策略，与 `stale-detector.ts`、`progress-classifier.ts` 分工。通过延迟/测量反例后才开启默认值。

## 8. 验收矩阵

### 确定性测试（明确不是模型能力评估）

使用缩短的测试期限和本地可控 provider/HTTP server，不在单测中等待 60/300 秒。至少覆盖：

- 首请求永不返回；headers 已到但 body 挂起；流式数据停滞。均按相应期限停止，非流式不误用 idle timeout。
- 第一次无工具请求超时，第二次成功：请求数为 2，失败 usage 未知，记录 retryOf；鉴权失败不重试。
- 请求超时后迟到返回 tool call；以及已排队工具在超时后开始执行：均不能产生动作。
- 已产生一次模拟写操作后 generate 报错：禁止重放；未知写结果保留核对状态。
- 取消发生在请求、退避、工具或收尾时：停止新调用，终态/统计只结算一次。
- page_act/transition 的耗时归工具，不被错误记成模型响应停滞；视觉请求仍受工具总期限约束。
- 业务成功但还有范围内必需调查：不能立即计为检查完成；超时后保存业务事实与未完成执行状态。
- 目标完成后进入收尾，模型试图继续购物被拒绝；两次收尾机会用完仍不 finish，生成明确部分报告。
- finish 缺证据被拒绝，不计作完成；收尾补齐后可接受，既有缺陷不消失。
- 重复观察/假设/截图 ID 不算新进展；正常异步反馈、5 秒必要测量及有用历史检索不被提前中断。
- UI/SSE 在请求未完成时就显示开始与 deadline；断开重连可读取完整阶段事件。
- 新停止原因不能通过 evaluator，旧报告仍可读，部分成功业务不能冒充完整 pass。

运行 `pnpm format:check`、`pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm test:fixtures`。测试失败应修复，不删除既有断言使新策略通过。

### 真实模型摸底：最多先跑六个案例各一次

继续使用已授权的 DeepSeek Agent 与 Qwen 视觉模型，模型/供应商配置、执行器版本及新增阈值写入清单。不临时替换模型或增加预算来挑选成功结果。

1. 先 smoke，再 C0 一次；C0 出现请求无界等待、错误终态、重复写或循环时先修复，不继续消耗其余案例。
2. C0 通过后跑 C1–C5 各一次。正式 API、私有重置和独立评估逻辑复用原方案，不将案例答案给 Agent。
3. 现有实验 runner 只验证 C0 操作任务，不能直接据其 pass 字段验收 C1–C5。需要提供独立的串行诊断入口，可复用 private controller/evaluator，但不得修改 `minimum` 套件必须六例各三次的约束。
4. 小批次逐轮保存：实际请求/重试、模型/工具耗时、首响应可用性、finish 尝试与拒绝、收尾触发原因、业务与执行结果、发现/证据/未覆盖、调用/token/成本。
5. C1 必须留证后恢复；C2 阻断真实结束；C3/C4 不误判；C5 的必要测量与无对应规则发现机会不能被收尾切断。任何失败保留原因；一期网络故障不能从分母删除。

单次摸底用于定位问题，不证明稳定性，不宣布 M3–M5 完成。配置稳定后另跑原计划的 C0–C5 × 3 正式验收；不混入此前调试轮次。

## 9. 交付与完成条件
