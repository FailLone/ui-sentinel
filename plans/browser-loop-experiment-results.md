# 浏览器循环实验结果

日期：2026-09-22。范围：C0 单商品购买、核验与结束；不是未知 UI 问题发现或完整 minimum 验收。

## 结论

在本次三组、每组三次的正式运行中，当前执行器 0/3 通过，Stagehand 3/3 通过，仅恢复动作历史的实验版本 2/3 通过。历史组未通过的那次在首个上游请求传输阶段失败，不能作为其推理能力失败的证据，也不能从成功率中删掉。

结果支持优先修复任务连续性和历史投影，尚不足以证明必须更换框架。a11y + text 可以完成这条购买任务；发送完整页面并不是完成任务的必要条件。是否能发现遮挡、输入区域误导或其他体验问题，本实验没有验证。

## 关键因果线索

当前执行器每步重新构造输入，历史中的一次成功点击通常被压缩为：

```json
{"tool":"page_act","url":"http://local-arena/"}
```

点击目标与参数消失，page_act 结果的页面文本也被剥离。相同 URL 下的加购、打开购物车、结账等动作难以区分。模型实际轨迹中反复“开始加入购物车”，页面购物车已有商品后仍重做，并反复观察。

current-history 只在隔离构建中做两项变化：内部保存真实工具结果，发送最近六步的动作参数、选定结果字段、ID 与证据。当前页面继续使用原来的 a11y + text；提示词、工具、模型、预算和定位代码未改，生产源码未改。

两次成功的历史组按正常顺序走完加购、查看购物车、结账、支付与结束。该结果支持“压缩丢失动作语义导致任务连续性受损”的假设，但不同运行的自动供应商路由与随机性仍是混杂因素。不能宣称这是所有超时的唯一根因。

Stagehand 的成功证明有可复用的开源完整循环，但它与当前执行器的系统提示词、内置工具、历史管理和重试行为均不同，因此不是仅改变一个框架变量的严格因果实验。

## 建议的后续实现

1. 修复历史契约：保留动作参数、动作结果、假设/证据 ID 和未知状态，用单一结构避免二次压缩丢字段。
2. 把已完成目标、当前调查和未覆盖分支存为独立任务状态，不让六条滚动历史承担全部长期记忆。
3. 修复上轮 review 中缺少元素 ref、歧义目标自动 first、a11y 相同误判无新事实、失败请求漏统计的问题。
4. 固定供应商与模型参数验证兼容性，把传输重试和业务写操作重试分别处理；不能因模型请求失败重放未知写操作。
5. 之后再跑 C0–C5 和探索类靶场，评估缺陷发现率。Stagehand 保留为对照与候选工具层，不立即整体替换。

本次历史变体是因果探针，不是生产修复：仅保留六步，仍不具备完整长任务记忆，不能直接当作最终上下文方案发布。
