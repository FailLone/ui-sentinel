# 最小可验证路径开发计划

日期：2026-09-20  
状态：待实施；本文不表示代码或实测已经完成。

依据：[总体架构](../docs/architecture.md)、[Agent 职责](../docs/agent-responsibilities.md)、[执行层](../docs/execution-engine.md)、[规则库](../docs/rules-and-rule-library.md)、[知识与上下文](../docs/knowledge-and-context.md)、[靶场库](../docs/arena-and-evaluation.md)。

## 1. 最终要看到什么

启动一个长期运行的 Server，打开同一入口提供的简单 Web 工作台，输入“检查购买流程”，选择已经准备好的测试环境。

Agent 自主浏览商品、购物车和模拟下单页面，使用少量已有规则，也能提出并验证没有对应规则的新假设。运行结束后看到问题卡、原始截图、标注或测量、执行时间线、业务结果和未覆盖范围。

确认一个探索发现后，Agent 提出规则候选；人工审阅并通过正反案例验证后启用。重新检查同类状态，展示规则复查结果与首次探索的成本记录。

该交付验证产品闭环，不追求一次覆盖所有架构模块。

### 1.1 给开发 Agent 的交接约定

阅读顺序：本计划 → 总体架构 → Agent 职责 → 按当前阶段读取执行、规则、知识和靶场专题。无需读取此前对话才能实施。

本计划决定本次交付范围，专题文档提供长期方向和约束，不能将其中全部功能加入本次任务。范围裁剪以本计划为准；权限、证据真实性、答案隔离和业务结果核对等约束不可裁掉。真实冲突应记录并澄清，不能静默更改验收门槛。

授权开发 Agent 完成 M0–M5 所需的常规实现决策，包括目录、库版本、数据库表、组件结构及测试组织，不需要逐项询问。按阶段连续推进，不以提交骨架或单次演示作为全部完成。模型凭据缺失、必须由人确认的规则发布、或不可消解的产品预期冲突需要明确提出；同时继续不依赖该条件的工作。

实现决策和阶段状态记录在 `plans/minimum-validation-progress.md`，避免将临时开发过程写入长期架构文档。记录已实现、已验证、待验证和阻断；真实模型测试未运行时不得标记整个计划完成。

## 2. 核心假设与通过证据

| 假设 | 需要看到的证据 |
| --- | --- |
| Agent 能自主探索 | 只给目标与入口，不给具体点击脚本，仍能到达相关页面状态 |
| 已有规则能稳定复用 | 同一规则在不同按钮文案或位置下仍有正确结果 |
| 无规则仍能发现问题 | Agent 登记假设、实施验证，并提交有证据的探索发现 |
| 自动恢复不掩盖质量问题 | 关闭 banner 后即使下单成功，仍报告原始阻挡和恢复动作 |
| 业务拒绝不等于检查失败 | 预期拒绝场景正确识别，且有明确原因依据 |
| 服务端独立运行 | 关闭工作台后检查继续，重新连接能读取进度和结果 |
| 经验可以沉淀 | 已确认发现形成候选规则，经正反验证后用于后续运行 |

不预先承诺规则复查一定更省 token；分别测量探索、定位和规则执行成本。未观察到收益也必须报告。

## 3. 范围

### 3.1 本次实现

- 单机 Mastra Server，一个本机浏览器执行节点；浏览器 worker 可用独立进程运行。
- 简单 Web 工作台：创建检查、进度、结果、问题确认和规则候选审阅。
- 一个购买靶场、一个测试账号、模拟库存与支付、可重置数据。
- Mastra Agent 作为探索主体，Playwright 与 Midscene 作为受控工具能力。
- 少量规则、假设记录、探索图的最小记录、发现提交与证据存储。
- 本地持久化任务/事件和文件证据，采用与锁定 Mastra 版本兼容的存储适配。
- 单个活动交互任务，其他请求排队；不提前实现多账号并发。
- 单步工作包与有限历史，保留必要要求、未决假设和副作用状态。
- 独立评估入口，使用产品正式 Run API 发起检查。

### 3.2 不在本次范围

- 多机器调度、共享资源分布式锁、远程画面流。
- 完整 PRD/Figma 自动解析、向量检索与大规模知识治理。
- 生产应用真实支付、消息发送及其他真实外部写操作。
- 全自动发布规则或修改产品规范。
- 完整恢复任意崩溃点；本次重启后先标记中断和核对，不盲目重放写操作。
- 完整管理后台和所有样式、可访问性或性能规则。

## 4. 开工前决策与配置

| 项目 | 处理方式 | 是否阻挡独立开发 |
| --- | --- | --- |
| Mastra / Playwright / Midscene / Node 版本 | 核对兼容性并锁定依赖，记录决策 | 影响执行接入，先完成小型兼容性验证 |
| 主 Agent 模型、视觉模型与凭据 | 显式配置；凭据放环境或秘密配置，不进日志 | 阻挡真实模型验收，不阻挡靶场与确定性模块 |
| 单轮动作、时间和模型预算 | 启动前配置并写入 Run；不设无界执行 | 影响实测，代码提供必填或有界默认值 |
| 靶场业务要求 | 将下单、拒绝、失败后重试等要求写入公开任务资料 | 影响答案定义，必须在评估前固定 |
| 本地存储 | 选兼容的持久适配与文件目录，核验重连可读 | 不要求提前选择生产数据库 |

不要求用户为了搭建骨架先解决所有问题。缺少凭据时完成可独立验证的部分，但明确模型集成尚未验证。

### 4.1 默认实现选择

- 包管理器使用 pnpm 并提交锁文件；Node 使用兼容所选依赖的受支持 LTS，记录在版本文件与 README。
- 前端使用 React + Vite，生产构建产物由 Server 同一入口提供；不增加另一套 Agent 编排框架。
- 单机持久化优先选择 Mastra 兼容的本地 SQLite/libSQL 适配，领域表亦使用本地持久数据库；证据文件位于 `data/artifacts/`。数据和秘密不提交 Git。
- 产品端口默认 4111，靶场端口默认 4173，可配置且冲突时给出明确错误。测试控制器不得通过 Agent 可访问的公共路由暴露答案。
- 默认每轮总时限 300 秒、最多 40 次改变页面的动作、最多 30 次模型请求；包含 Midscene 内部模型调用。达到预算停止新工作，保存已有证据和未完成项。
- 单工具操作默认上限 15 秒；等待页面稳定、业务反馈和恢复各自显式配置，不能将所有等待写成固定 sleep。

这些是本次工程默认值，不宣称经过性能验证。常规兼容性调整可以由开发 Agent 决定并记录；模型成本预算、动作权限和验收门槛不能在评估后为提高成绩而偷偷放宽。

### 4.2 模型配置与缺失处理

提供 `.env.example` 和启动校验，至少说明主 Agent 的 provider/model、视觉模型、各自的凭据变量、可选 endpoint，以及运行预算。可使用项目配置键 `AGENT_MODEL`、`VISION_MODEL`；provider 的凭据与 Midscene 实际参数由适配器映射，具体名称按锁定版本核对。

不把模型名硬编码在业务工具或靶场中。模型需用户提供或确认，不能擅自消耗未经指定的账户。记录真实运行的模型标识、用量和适用的推理配置；用量不可获得时标记 unavailable，不记为 0。

缺少模型配置时，Server、Web、靶场和确定性测试仍可运行；创建需要模型的 Run 返回明确的 configuration-missing 错误，不返回假成功。可用 mock 做接口测试，但单独标识，不进入 M4 分数。凭据补齐后必须运行真实模型 smoke 和正式评估。

## 5. 靶场案例矩阵

同一购买应用提供以下六个变体。变体 ID 和答案由评估控制端管理，被测 Agent 不读取私有配置。

| ID（评估端） | 条件 | 预期 |
| --- | --- | --- |
| C0 | 正常购买 | 模拟下单成功，无预置缺陷 |
| C1 | 活动浮层阻挡提交，可关闭 | 发现阻挡，保存原始证据；恢复后可继续 |
| C2 | 活动浮层阻挡提交，无有效关闭入口 | 发现阻挡，正确报告路径受阻 |
| C3 | 正常按钮改名和移动，但保持合理可见布局 | 不把正常变化误判为缺陷，仍完成任务 |
| C4 | 测试支付按预期拒绝，原因明确且恢复入口正常 | 正确业务 rejected，不误报为路径逻辑失败 |
| C5 | 支付失败提示可重试，但操作持续不可用 | 无直接对应规则时，Agent 自主验证恢复异常 |

公开要求包含“支付失败后应允许重试”，不泄露 C5 的实际故障。开发 Agent 会实现并知道 C5，因此它是“运行时无对应规则的发现测试”，不是严格的开发者未见保留案例。首轮冻结运行配置后执行 C5，记录是否做过针对性调优；不得将其结果描述为完全未知问题的泛化能力。真正保留案例需开发完成后由独立人员或隔离流程提供，不属于本次必需交付。

各变体通过独立断言验证应用条件，具备数据重置和固定构建记录。不能将未触发或失效的案例计为通过或漏报。

## 6. 开发阶段与依赖

执行顺序：M0 → M1 → M2 → M3 → M4 → M5。每个阶段产出可运行结果，不以“架构代码写完”作为验收。

### M0：兼容性与项目骨架

工作：

- 建立 TypeScript 项目、依赖锁与启动配置。
- 验证 Mastra Server、一个带 schema 的工具、Playwright 页面和 Midscene 定位适配。
- 将模型调用置于配置边界，明确取消与错误如何传递。
- 确定单机持久化适配及证据目录。

产物：可启动 Server、健康接口、最小工具调用示例和依赖记录。

验收：浏览器能打开普通测试页并保存截图；有模型凭据后完成一次真实的语义/视觉定位。无凭据时不能把 mock 结果标为模型验证成功。

### M1：可控购买靶场

工作：

- 实现商品、购物车、订单和模拟支付结果，准备测试账号。
- 实现 C0–C5 变体、数据重置和独立有效性检查。
- 分离公开任务资料、靶场应用和私有评估器。
- 配置 Agent 的访问范围，避免经文件、接口或日志读到答案。

产物：可手动浏览的靶场与自动准备/重置命令。

验收：每个案例的故障或正常条件可由独立程序验证；重置后数据一致，私有答案不出现在 Agent 输入中。

### M2：服务端任务与 Agent 探索闭环

工作：

- 创建异步 Run API，立即返回 runId；实现查询、取消和带游标事件订阅。
- 工具优先实现 page.observe、page.act、checks.run、hypotheses.record、findings.submit，以及最小 exploration.update。
- 此阶段建立规则注册接口、动作前后 Hook 和空规则集的真实记录；M3 再接入具体规则。checks.run 在没有规则时返回 evaluatedCount=0 和 not-checked 摘要，不能返回页面通过。
- Agent 从业务目标自主寻找操作，不注入按案例定制的 selector 或固定点击脚本。
- 最小记录状态、待办分支、假设和停止原因；不实现多 Agent 分叉。
- 封装资源申请、动作前后取证、超时和清理，固定一个活动交互任务。

产物：简单 Web 表单启动检查，展示状态与事件列表。

验收：C0 能到达业务结果；关闭 Web 后继续执行，重连能读到完整任务记录。取消后停止新动作并清理可清理资源；结果未知的写操作不重复发出。

### M3：少量规则与真实证据报告

工作：

- 实现 2–3 项明确能力：活动浮层阻挡、业务终态验证、配置的响应时间预算。
- 规则读取共享快照；事件变化后按需重查，模型不加载规则源码。
- 问题卡显示预期、实际、依据、步骤、原始截图、必要测量和恢复记录。
- 可靠 DOM 坐标生成标注副本，原图保留；视觉估计和证据不足明确标识。
- 规则与 Agent 发现使用不同来源关联，业务结果与检查结果分开。

产物：可浏览的运行报告和机器可读结果。

验收：C1/C2 正确报告阻挡；C1 在关闭前留证，恢复成功不撤销发现；C3/C4 不因正常改动或预期拒绝被判失败。

### M4：独立评估与无规则发现

工作：

- 评估控制端通过正式 Run API 发起案例，收集报告与证据。
- 评分发现、误报、证据、路径到达、执行越界和成本，保留基础设施失效记录。
- 首次冻结配置后运行 C5，要求通过假设与操作证据验证，不能提前添加等价检测规则。
- 对固定配置重复运行六个案例，每例至少 3 次，全部报告；这只是小样本工程门槛，不是统计可靠性证明。

产物：版本对照的评估表，失败可回看对应 Run。

本轮放行门槛（评估前固定）：

- C0/C3/C4 三轮均正确判定业务结果，且不对预置合理行为报错。
- C1/C2 三轮均发现阻挡并保留原始证据。
- C5 至少两轮产生有充分证据的恢复异常发现，其余运行明确记录失败原因。
- 所有运行没有越界写入、答案泄露、重复模拟下单和伪造证据。
- 各轮遵守事先固定的预算；未完成与 invalid 不混成通过。

若出现预置答案之外的新发现，独立核验后再判定，不自动当误报或命中。门槛未满足则按阶段失败归因修复，不临时降低门槛以宣告完成。

### M5：反馈到规则复查

工作：

- 在工作台确认一个探索发现，例如 C5 的恢复异常。
- Agent 提出项目级 transition 规则候选，明确前后状态、等待预算、适用条件和依据。
- 本轮只生成受限声明式规则配置，不执行任意模型生成的 JavaScript，也不建设通用代码沙箱。规则引用已注册的事实和条件运算符；校验 schema、适用范围、证据依赖并跑正反案例。
- 人工审阅后发布修订；不允许模型直接修改正式规则与评估答案。
- 重跑同类异常及正常恢复变体，比较首次探索与规则复查的模型调用、耗时和结果。

产物：发现 → 确认 → 候选 → 验证 → 启用 → 复查的关联记录。

验收：候选在异常案例 fail、正常恢复案例 pass、缺少事实时 unknown；启用后可稳定复查。C5 此时属于已见回归案例，不能再用于证明未知问题发现能力。

本次声明模板支持：匹配 transition 类型、前后业务状态条件、布尔值/枚举相等、时间窗口及 unknown 传播。例如“收到可重试的支付失败后，5 秒内应提供可操作的重试入口”。通用事实采集可以事先实现，但 M4 前不能内置这条等价质量判定。需要超出模板的规则时记录 unsupported，不偷偷执行自由代码。

## 7. 交付组织建议

```text
src/
  server/          # Mastra 与产品 API，Web 静态入口
  agent/           # 探索指令、工具、工作包
  execution/       # Run、动作、资源与浏览器适配
  rules/           # 最小规则引擎与内置规则
  storage/         # 运行、事件和证据
  web/             # 创建检查、进度、问题与候选审阅
arena/
  checkout/        # 应用、变体与重置
evaluation/
  private/         # 运行时不提供给被测 Agent
```

目录为组织建议，技术默认值见第 4 节。目录隔离本身不能替代运行权限和文件挂载隔离。

## 8. 最小数据与恢复要求

至少持久保存 Run、任务/动作状态、事件、快照引用、规则结果、假设、发现和候选修订，以及模型/工具/规则/靶场版本。

Web 断开不影响执行；Server 重启后仍能查看历史。运行中发生重启时，任务标为 interrupted/reconciliation-required，核对外部状态后再决定重试或终止。本轮不承诺自动无缝续跑。

截图和 DOM 使用文件引用，秘密与敏感输入按配置处理。正式业务事件不依赖可丢弃的调试日志。

## 9. 每阶段向用户展示的结果

- M0：Server 启动地址、健康状态、一次工具与浏览器验证。
- M1：正常和异常页面的可运行靶场。
- M2：输入目标后 Agent 自主执行的实时事件列表。
- M3：包含真实现场与依据的问题卡。
- M4：六个案例全部运行的评估表与失败证据。
- M5：一项问题沉淀并用于复查的完整记录。

开发完成报告需区分已实现、确定性验证、真实模型验证和未验证内容。不能用固定报告、预录操作、mock 模型或答案注入替代最终验收。

## 10. 完成条件与后续范围

本计划完成意味着：单机服务可用，Agent 能自主探索可控购买应用，有规则和无规则两条发现路径均有实测证据，报告可核实，人工确认后能够沉淀并复查。

完成后先接入一个真实测试应用，观察靶场与真实页面的差异，再决定是否优先扩展资料导入、知识检索、多账号或分布式执行。不得仅凭靶场通过宣称能可靠检查任意 Web 应用。

## 11. 最小接口契约

将以下契约集中为 schema，供 API、Web、评估器和测试共享。路径是项目 API，不假设是 Mastra 内置路由。字段可以增加，但状态语义不能各端自行解释。

| 接口 | 最小约定 |
| --- | --- |
| GET /api/health | 返回进程健康、存储状态、模型配置是否就绪；不返回秘密 |
| POST /api/runs | 接收 goal、environmentId、可选 budget；202 返回 runId、status、eventsUrl、reportUrl |
| GET /api/runs/:id | 返回 Run 状态、业务结果、stopReason、预算消耗和最新事件序号 |
| POST /api/runs/:id/cancel | 幂等请求取消；返回请求是否接收，不将接收等同于清理完成 |
| GET /api/runs/:id/events | SSE，支持 after 游标或 Last-Event-ID，从持久事件补发 |
| GET /api/runs/:id/report | 返回完整或部分报告，包含 findings、evaluations、coverage、usage、evidenceRefs |
| GET /api/runs/:id/artifacts/:artifactId | 按证据 ID 读取文件，不能接受任意磁盘路径 |
| POST /api/findings/:id/feedback | 接收 confirmed、intentional、cannot-reproduce、deferred 及原因 |
| POST /api/rule-proposals | 引用 findingId 发起规则候选生成，返回可追踪的候选 ID |
| GET /api/rule-proposals/:id | 返回候选配置、依据、正反案例验证和审阅状态 |
| POST /api/rule-proposals/:id/review | 接收人工 approve/reject；仅验证通过且批准的修订可以启用 |

人类审阅接口不注册为被测 Agent 工具。最小版本仅用于受信本机环境，默认绑定 loopback；跨主机访问或面向不可信用户开放前另行实现认证，不把未做认证的演示宣称为生产服务。

Run 状态固定为 queued、running、completed、blocked、timed-out、cancelled、execution-error、interrupted。业务结果独立为 success、rejected、unknown；重启后有未决写操作时，stopReason 为 reconciliation-required。取消请求与最终 cancelled 分开记录。

事件最小字段为 id、runId、seq、type、timestamp、stepId/actionId（适用时）、payload、evidenceRefs。seq 在 Run 内单调递增；客户端按 ID 去重，重连不能改变或重复执行业务动作。终态先持久化，再向订阅者发送完成事件。

Finding 包含 id、source（rule/agent）、ruleId+revision 或 hypothesisId、validationStatus、severity、title、expected、actual、stepId、evidenceRefs。supported 必须有有效证据引用；没有证据的模型输出保留为 candidate/inconclusive。

报告至少列出已到达状态、未探索分支、已执行规则、unknown、执行错误和停止原因。evaluatedCount=0、业务 unknown 或预算耗尽不能展示成“全部通过”。模型输入/输出 token、调用数与浏览器动作数分别保存；金额只有在定价来源明确时才计算。

## 12. 评估判据与独立答案

### 12.1 预先固定的公开业务条件

- 主要提交操作不得被活动内容阻挡。
- 支付拒绝必须显示明确原因，业务结果可为 rejected。
- 可重试失败的反馈出现后，5 秒内恢复可操作的重试入口；Agent 可以知道这个要求，但不能知道哪个变体违反它。
- 系统响应超过 10 秒记 warning。区间按实际动作发出到对应反馈可见，不包括模型推理和下一次人工/Agent 决策等待。

数字是本靶场产品要求，不推广为通用 UX 标准。用浏览器侧观测或有界轮询记录时间与采样误差；边界落在误差范围内时 inconclusive，不能强行判定。

### 12.2 具体命中与正常判据

| 案例 | 私有评估依据 |
| --- | --- |
| C0 / C3 | 模拟后端确认唯一订单/支付成功，页面展示同一业务结果；没有针对预置合理行为的 supported 缺陷 |
| C1 | Agent 到达提交状态；关闭前截图和命中测试证明活动层截获目标区域；发现关联正确步骤；关闭后操作可继续 |
| C2 | 独立评估确认主要操作持续阻挡且无有效关闭路径；Agent 保留现场并报告 blocked，不强制点击或移除 DOM |
| C4 | 后端与页面反馈均为预期拒绝且原因一致，重试入口按时可用；不把拒绝本身报告为失败 |
| C5 | Agent 记录恢复异常假设与验证，失败反馈后观察至少 5 秒，证明重试入口持续不可操作或缺失；无先验等价规则，无答案注入 |

遮挡检测不能仅用矩形相交：记录目标定位依据、原始视口、代表性命中采样及阻挡元素关系；必要时结合非强制的可操作性探测。若探测会自动滚动，原始截图必须先保存，并记录该准备动作。目标中心被挡但其他区域仍能操作时，只报告实际覆盖事实，不能概括为完全不可点击。

C5 无规则发现的验证可以复用测量 API，不允许将固定故障检测藏在 page.observe、提示词、专用 selector 或案例 ID 分支中。运行时产品工具不得获取评估变体 ID；正常环境引用应保持中性，公开任务仅提供业务条件。

时间规则除六个主案例外，增加不调用模型的快/慢响应测试：例如 0.5 秒和 12 秒，用于验证 10 秒阈值、起止事件和计时；它不作为第七个 Agent 泛化案例。M5 另配正常可重试、不可重试异常和缺失事实三个正反输入。

### 12.3 评估独立性与失败处理

私有控制器通过后端业务状态和确定性断言验证案例，不以被测 Agent 输出作为案例正确的证明。证据匹配使用对象、条件和测量而非标题关键词；对语义歧义或答案外发现标记 needs-review，不自动算命中。

开发 Agent 可以实现应用和评估器，但需将答案断言、产品检测逻辑和运行时权限分开。首轮结果提交人工抽查，不能声称同一开发者实现的评估已经等同于独立第三方验证。

每例三次是固定配置下的预定运行集合。invalid 和执行错误保留原记录，需要补跑时明确原因，不覆盖或删除原分数。修复后创建新批次并记录修改；不得从不同批次拼选三次最好成绩。
