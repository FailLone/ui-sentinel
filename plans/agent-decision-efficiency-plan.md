## 目标与现有证据

本轮要回答：哪些模型等待来自必要决策，哪些来自信息契约造成的额外往返；改进当前执行器或采用开源完整 Agent 循环，哪一种能在相同检查质量下缩短交付时间。

目标是在明确任务、质量与成本约束下找到证据支持的更优方案，不宣称全局最优或今后无需调整。允许扩大到工具契约、历史组织、决策循环和执行框架，但每项变化必须有独立假设与可审计对照。

最新默认路径六例数据来自 `data/acceptance/2026-09-23T15-47-07-984Z/`：

| 指标 | 结果 | 可以说明什么 |
| --- | --- | --- |
| 六例总耗时 | 332.232s | 本次诊断的交付耗时基线 |
| 模型决策等待累计 | 308.325s，约 93% | 主要时间花在等待模型；不等于全部是模型固有速度 |
| 含收尾决策的请求等待 | 38.205s，约总耗时 11.5% | 收尾有成本，但单独优化它不足以解释主要长尾 |
| C2 与 C5 耗时合计 | 229.593s，约 69% | 优先审计这两类决策 |
| 模型请求失败 | 0 | 这批慢不能直接归因于请求失败重试 |
| output / reasoning tokens | 30,055 / 27,341 | 推理占输出约 91%，不能据此推算推理耗时比例 |

这些是六例诊断，不是最新版本正式十八轮验收。供应商排队、prefill、内部推理和输出生成的耗时尚未分离；响应头时间不等于首 token 时间，首个可见 delta 也未必包含推理过程。

上一轮已实现短收尾及冻结证据并行，但没有通过提速验收；新增视觉巡检也没有通过质量门槛，继续默认关闭。历史 Stagehand 实验只覆盖购买操作，不能证明当前版本的检查能力优劣。Browser Use 尚未进行完整 Agent 实测；Midscene 已用于视觉定位，不等于验证了其完整 Agent 循环。

## 固定边界与评估口径

- 默认沿用 DeepSeek 主 Agent、Qwen 视觉模型及原供应商、reasoning 配置。型号可用性在开跑前确认并冻结；不可静默替换。模型或供应商实验另立批次，不混入工具契约收益。
- 每轮沿用 300 秒、30 次实际上游请求、40 次动作，单请求 60 秒、最多 4096 输出 tokens、最多一次符合原安全条件的恢复。视觉、框架内部请求与重试共享预算，不增加上限换通过。
- 视口、初始业务数据、任务目标、可用规则、证据要求、历史起点一致。未知发现组不加载已学会的 C5 规则；批准规则复查另行隔离，源数据库不变。
- 所有方案必须保留未知问题探索、正常完成或预期阻断、可信证据和主动结束能力。正常购买成功不能代替 UI 检查通过；超时强制停止不能冒充 Agent 完成。
- 区分 pointer-interception、像素覆盖和视口裁剪；命中采样不能证明像素覆盖。不引入现阶段无法独立验证的视觉判断作为通过依据。
- 默认后台视觉巡检关闭，既有按需视觉定位可用。需要新增视觉任务时独立定义质量门槛，各对照组执行同一任务。
- 使用统一上游记账、外部评分和原始证据。记录全部失败、超时、未知 usage 与费用；框架生成次数、工具次数、实际上游请求次数分别统计。
- 付费前冻结批次清单：假设、提交、依赖版本、输入哈希、样本数、顺序、停止条件、美元预算、模型配置和评分协议。沿用原凭据配置，不将密钥或原始敏感请求提交 Git。

## P0：逐请求解释 C2、C5 的慢决策

先审计已有记录，不调用付费模型。对最新默认路径 C2、C5 的全部模型请求，形成可回溯的决策表：

| 字段 | 要回答的问题 |
| --- | --- |
| 请求与输入事实版本 | 模型当时实际看到了什么，而不是数据库里理论上有什么？ |
| 本步目标与未决问题 | 为什么需要这次决策？是目标定位、规则匹配、证据核验还是结束？ |
| 已有证据与缺失证据 | 所需信息是否已在本次输入中、能否有效定位、是否已经过期？ |
| 工具参数、结果与新增事实 | 同名工具是否查了不同对象？本次是否减少了不确定性？ |
| 前置依赖 | 必须等待上一步结果，还是可以合并交付或独立读取？ |
| 时延与用量 | 请求耗时、可见流时间、input/output/reasoning、重试与可观测限制 |
| 优化假设 | 信息丢失、碎片化检索、重复核验、结束歧义、必要探索或原因未知 |

不要按重复工具名自动判定浪费；需要核对参数、结果、页面版本和语义目的。必要等待与有价值的探索明确保留。收尾请求单列，避免把所有收益寄托于 `run_finish`。

产物：`plans/agent-decision-efficiency-results.md` 的基线审计与假设表，脱敏逐请求表及本地原始记录索引。每个拟改动至少绑定一个真实决策状态和可证伪预测。

完成条件：可以解释两例全部模型往返；无法解释的项明确标为未知。选出最多一个首轮信息契约候选，避免同时更换提示词、工具、模型和历史。

## P1：固定输入重放，验证信息契约

优先候选是有界的调查上下文：一次交付当前目标的元素事实、相关规则摘要与已完成检查、仍缺失的证据及其引用，减少分散的 `element_details`、`rules_search` 和结果读取往返。是否采用由 P0 决定，不预设组合工具一定更好。

实现要求：

- 每项事实保留来源、页面/证据版本和有效范围；过期事实不能默认为当前状态。
- 有大小上限和按需读取入口；不能退回每轮完整页面，也不能把所有规则塞进上下文。
- 保留待证实问题和探索入口；“已经做过检查”不能直接推出“整个页面没有问题”。
- 不把 evaluator 的答案、case ID、私有业务状态或人工标注注入模型。候选只组合该时刻通过公开工具合法取得的事实。
- 组合所需的读取、预计算和视觉请求计入成本；不能把工作移出 Agent 请求后便当作免费。

从 P0 冻结六个代表性决策状态：规则检索、重复观测/核验、收尾各两份，覆盖 C2、C5。冻结选择理由，避免只挑候选容易通过的状态。

第一批每状态两种契约各两次，共最多 24 次模型请求；交替顺序，无真实工具副作用。人工预先定义可接受的下一步集合及证据约束，允许多种合理动作，不要求命中某个固定工具名。原始组与候选组除信息契约外保持一致。

重放比较有效决策、证据引用准确性、错误完成、遗漏必要核验、耗时和全部用量。重放只能证明这些冻结状态的下一步质量；后续请求数和端到端收益必须再测，不能外推。

进入端到端的条件：候选没有新增的错误完成或错误证据支持，在冻结状态上减少了已定位的契约问题，且没有删除必要任务。阴性或不确定结果归档，不靠不断换输入重试。最多允许一次由明确实现缺陷触发的修正批次；不得超过同规模上限。

## P2：实测开源完整 Agent 循环

无论 P1 是否取得收益，都补齐开源对照。比较当前执行器、Stagehand、Browser Use；先检查官方源码/文档、许可证、模型兼容性并锁定版本。实现独立实验适配器，不直接替换产品默认执行器。

这里比较的是完整执行方案：框架自己的循环、观察、历史和工具策略都应实际运行。不能仅让现有 Agent 调一个开源工具便称为完成框架对比。由于提示词、历史和工具组织不同，结果是整体方案比较，不能归因于框架名称这一个变量。

适配器统一输入任务、预算、浏览器初态、证据导出和结束语义；允许各方案使用其原生工具和历史组织。保留相同规则事实与验证能力，不强制使用本项目的工具名称。Agent 可以主动选择结束，适配器只规范映射其状态，不替它推断完成。

共同任务至少包括：

| 场景 | 必须验证的能力 |
| --- | --- |
| C0 健康购买 | 完成关键路径、核对结果、没有错误缺陷、主动结束 |
| C2 遮罩阻断 | 发现指针拦截、正确解释阻断、关联有效证据、避免虚构像素覆盖 |
| C5 未知重试缺陷 | 在没有学习规则的条件下提出假设、按现有证据标准验证、报告与结束 |

评估沿用各场景已有检查要求与独立业务核对，不向被测 Agent 暴露答案。只会购买而不能接入缺陷证据/验证的方案应记为能力不完整，不能与完整检查运行比较速度。

所有主模型、视觉及框架内部模型调用经统一网关记录。若方案必须更换模型、使用隐藏模型或无法可靠计费，标为当前约束下不兼容；可记录另一个研究方向，但不得静默组成不公平对照。

实验分两步：

1. 适配和预检：优先使用确定性替身与真实本地浏览器检查预算、取消、证据、隔离和完成映射。每个开源适配器最多两次真实模型连通性预检；不计入效果评分。
2. 第一轮完整比较：三方案 × C0/C2/C5 各一次，共九轮。若 P1 有合格候选，增加该候选三轮，共最多十二轮。当前基线始终保留；所有组冻结并交替运行，避免连续运行一个方案造成时段偏差。

第一轮仅用于排除能力或质量不合格方案、选择最多一个候选进入 P3，不能凭单轮时间宣布胜出。完整记录 Stagehand、Browser Use 是“成功运行”“能力不完整”“配置不兼容”还是“运行失败”。不能再把源码阅读写成已验证的方案。

## P3：独立复验与采用决策

对 P2 选出的一个候选与当前基线做新批次：C0/C2/C5 各三对，共十八轮，冻结后交替运行。它是性能与检查质量复验，**不是 minimum 的 C0–C5 正式十八轮验收**，两者名称和记录必须区分。

采用门槛在运行前固定：

- 两组均通过全部规定场景的检查质量、证据、主动结束和副作用约束；不能只比较成功子集，失败率单列。
- 候选总报告可用时间至少下降 15%，实际上游请求数不增加，完整费用不增加。报告各场景分布，不能只给总和掩盖某类明显退化。
- 记录主模型与视觉用量、首个有效发现、任务完成、报告持久化可读时间。客户端未测时，不把服务端终态时间称为用户实际看到报告的时间。
- 缺失 usage、供应商变化或任务量不同，不能宣布完整性能/费用门槛通过；小样本只支持本批任务范围的结论，不宣称稳定 P95。

若速度与费用形成取舍，明确列出结果和代价，不自动改动采用门槛。未通过时保留当前默认方案；实验完成与优化通过分开勾选。

候选通过后才进入产品整合：保留回退路径，补充受影响契约测试，完成类型、构建、格式及靶场隔离验证，再运行最新代码的真实 smoke、C0–C5 诊断；诊断通过后执行正式 minimum 十八轮。涉及学习流程时执行批准规则复查，并核对源数据库未变。产品验收另立清单，不把研究批次充当发布验收。

## P4：有条件地重新验证并行

只有 P0–P3 找到可独立进行、质量已可验证且占用关键路径的工作，才进入本阶段；否则记录“不满足触发条件”，不为了并发而增加任务。

候选限于冻结证据上的独立检索或分析。保持单个活页面操作者；共享账号的业务写入、依赖最新页面的定位、时序测量不得随意并行。规则检索的参数若依赖前一动作结果，也不能提前猜测后执行。

先画实际依赖关系，估算可重叠时长及调度、汇总、新发现验证的额外成本。用确定性任务确认取消、预算、过期结果和收尾等待正确后，冻结同一任务集合做串并行比较；最多两个代表场景、每场景两对，共八轮。采用 P3 相同质量与性能门槛。

必须比较全部结果可用时间，不能只报告后台任务重叠率。新增检查能力与调度提速分别评价；上一轮质量不合格的视觉巡检不能直接重新作为提速候选。

## 实验上限与停止规则

本计划按门槛逐段推进，不预先启动整个矩阵。首批上限：P0 不付费；P1 为 24 次请求；P2 为四次适配预检、十二轮完整任务；P3 为十八轮；P4 满足前提后为八轮。仅明确实现缺陷允许一次不超过原规模的修正批次，因此各阶段累计硬上限分别为 P1 48 次请求、P2 八次预检和二十四轮、P3 三十六轮、P4 十六轮；这不是必须用满的额度。产品验收另算并显式列出。

每批根据当前价格和既有用量先写入美元上限，执行器预留在途额度并强制止损；用量未知保守占额，不能按零处理。不得“直到通过”为止追加运行。

- 数据泄漏、重复业务写、失控计费、证据错配：立即停止相关批次并保留记录；不得继续收集看似可用的成绩。
- 普通质量失败、上游失败、超时：按预声明策略记录并完成剩余安全样本，不删除、不单独补跑失败项。
- 发现明确实现缺陷：冻结失败批次和原因，最多一次针对性修正；新批次不与旧成绩拼接。P2/P3/P4 如需修正复验，也不得超过各自原批次规模；再次失败则交付阴性结论。
- 无候选达到质量门槛：结束该分支，继续尚未完成的独立研究；没有候选进入 P3 时，不运行空洞的性能对照。
- 预算耗尽或证据不足：交付当前结论与未解决问题，下一轮范围另定，不自行扩大预算、模型输出上限或实验次数。
