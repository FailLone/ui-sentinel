## 1. 核心定位

Agent 是应用的检查主体：决定探索哪里、怀疑什么、怎样验证，以及哪些经验值得复用。应用不要求人工预先穷举页面、状态、操作路径或规则。

各层分工：

| 层 | 核心职责 |
| --- | --- |
| Agent | 理解、探索、提出假设、组织验证、解释结果和提出改进 |
| 执行层 | 可靠操作、资源隔离、自动检查、证据与日志 |
| 规则库 | 将已明确的判断沉淀为低成本、可重复的检查 |
| 知识库 | 保存产品意图、已知事实、路径、案例和经验 |
| 上下文构建器 | 为当前任务提供必要知识和工作状态，控制上下文规模 |

Agent 运行、工具调用和可复用工作流由 Mastra 承载，项目保留探索、质量判断和资源策略。Mastra Studio 服务于开发调试，用户使用产品自己的工作台。

Agent 不只是脚本失效后的补救机制。没有适用规则也可以探索和报告新问题；已有规则用于提速、保持一致性和节约 token。

Agent 也不能穷举所有可能状态。报告需要明确已检查范围、未探索分支、未决假设和停止原因，不将“未发现问题”描述为整个应用没有问题。

## 2. 八项主要职责

### 2.1 理解目标和产品

读取用户目标，以及相关 PRD、Figma、设计规范和历史知识，形成对业务意图、检查范围和预期行为的理解。

- 区分明确要求、实际观察和待验证推断。
- 识别资料冲突、版本差异和缺少的条件。
- 不以当前实现自动定义正确要求。
- 不依赖冲突的工作可以继续；确需产品判断的事项单独提出。

产物：任务目标、范围、预期依据、知识引用和待确认事项。

### 2.2 理解当前界面

结合当前 DOM、截图、上下文和知识，识别页面用途、主要操作、组件语义和业务状态。

- 将“提交订单”等业务意图映射到当前界面，而非依赖固定标签或位置。
- 区分同一 URL 下的初始、弹窗、加载、错误和成功等状态。
- 定位和语义不明确时保留歧义，不能猜测后直接操作。

产物：页面语义、目标候选、操作映射和带证据的状态记录。

### 2.3 持续规划探索

维护逐步扩展的探索状态图，选择页面入口、交互分支、关键路径和边界条件。

- 根据业务重要性、近期变化、未知程度和预算调整优先级。
- 复用已知 Journey，也能在没有完整路径定义时开始探索。
- 发现新状态后重新规划，不只执行开始时生成的静态清单。
- 避免无目的重复操作；有意复现或跨环境验证需记录目的。

产物：探索状态图、待办分支、优先级依据、覆盖记录和停止原因。

### 2.4 组织执行任务

通过工具创建有边界的任务、选择可复用检查点、提出动作请求，并根据返回结果继续、等待、恢复或结束。

- 子任务分叉是计划决策；是否并行由资源调度器决定。
- 处理 blocked、unknown、歧义目标和结果未知等反馈。
- 已授权恢复可以继续执行，但不能抹掉原始问题。
- 不绕过资源锁、权限、预算或重复提交保护。

产物：任务图、动作请求、验证计划和必要的恢复决策。

### 2.5 使用已有规则

在规划、到达状态、调查假设、动作前后和路径结束时使用已有规则。

- 检索规则清单，利用已知约束安排需要覆盖的场景。
- 主动调用相关规则验证假设，读取结果决定是否深入调查。
- 已有事实与规则结果可复用，不重复消耗模型推理。
- 规则未命中不结束探索；规则 unknown 也不当作通过。

执行层仍自动保障基础规则和生命周期检查。Agent 的主动规则选择不替代这层覆盖保证。

产物：主动选择依据、规则结果解释、补充调查任务。

### 2.6 发现并验证新问题

能验证已给定的问题，不代表会自主产生相应假设。Agent 需要按页面状态检索探索策略，主动尝试边界、留白和替代操作，而不能只依赖任务失败触发调查。策略引导“去哪里找”，规则判断“已有事实是否违规”；没有适用策略时仍允许自拟调查方向。契约、输入框案例与发现能力评估见[探索策略与未知问题发现](./exploration-strategies.md)。

根据需求、任务目标、同类规律、操作承诺和前后状态关系建立预期，识别异常线索并提出可证伪假设。

```text
发现线索
  → 提出假设和预期依据
  → 明确验证动作与所需证据
  → 调用已有规则或组合底层能力
  → 检查合理的替代解释
  → 支持、反驳或无法判断
```

例如怀疑“取消编辑后仍保存修改”，应检查产品是否采用自动保存、是否有并发写入以及结果是否持久化，不能只凭一次视觉变化下结论。

没有对应规则时，以假设和验证记录关联发现，不伪造 ruleId。新问题可以先报告，随后再判断是否值得沉淀。

产物：有证据的发现、被反驳的假设、无法判断项和独立展示的体验建议。

### 2.7 解释与汇总结果

将技术现象与业务影响关联，组织证据和复现条件，说明结论及其边界。

- 区分业务结果、执行状态和检查结论。
- 任务最终成功不表示体验通过，自动恢复造成的额外操作仍需报告。
- 聚合同类问题但保留原始证据，不因汇总丢掉 unknown 或冲突。
- 改进建议标明依据和适用条件，例如 sticky 是候选方案而非所有页面的正确答案。

产物：问题解释、运行总结、建议及已知覆盖边界。截图、测量、报告事实和持久存储由执行层提供，Agent 不凭空补全证据。

### 2.8 从反馈中改进

分析误报、漏报和人工纠正，区分探索缺失、采集不足、规则遗漏、判定错误、恢复掩盖现场或报告聚合问题。

- 提议修正规则、场景、语义映射、探索策略或工具协议。
- 将确认的问题沉淀为回归案例，并验证合理例外。
- 知识候选需标注来源、范围、版本和确认状态。
- 观察到的行为不能自动成为规范；模型建议不能自动成为人工确认的规则。

产物：知识候选、回归案例和有证据支持的修改建议。正式发布遵循各类知识与规则的审阅和验证策略。

Agent 也是靶场候选案例的来源：可以整理真实漏报并发起隔离的案例构建任务。开发团队维护测试框架和基础答案，独立评审流程核验案例有效性与预期；被测 Agent 不能修改正式答案或自行给自己评分。具体分工见[验证靶场库与持续评估设计](./arena-and-evaluation.md)。

## 3. 整体工作循环

```text
理解目标与相关知识
  → 观察并理解当前界面
  → 更新探索图，选择下一项调查
  → 创建任务、复用检查点或提出动作
  → 使用规则或验证新假设
  → 分析证据并更新计划
  → 报告发现、未知与覆盖边界
  → 根据反馈提出知识更新
  → 在预算和范围内继续探索
```

规划、观察和判断持续交替。例如发现活动浮层后，可以增加“是否遮挡提交操作”“是否遮挡错误反馈”“关闭后是否再次出现”等分支。引擎自动执行已有检查，Agent 重点处理新信息和未解决的问题。

## 4. 角色划分与上下文

八项职责不对应八个独立 Agent，也不要求不同模型。可以使用主 Agent 与任务 Agent 的逻辑分工：

| 角色 | 工作范围 |
| --- | --- |
| 主 Agent | 全局目标、探索计划、任务组织、预算内优先级与结果汇总 |
| 任务 Agent | 当前页面或路径的理解、具体假设验证、局部探索扩展 |
| 确定性执行分支 | 规则批量检查、事实采集和固定流程，不需要模型会话 |

创建任务 Agent 必须有明确目标和工作边界。是否并发取决于账号、业务资源和预算，不由 Agent 数量决定。

每个 Agent 获得当前工作包，不加载整个知识库或所有分支对话。父任务收到结构化结果和证据引用，必要时展开。持久任务状态是恢复依据，摘要不能丢失权限、未决写操作或关键冲突。

## 5. 不依赖 Agent 自觉执行的保证

| 执行层保证 | Agent 的边界 |
| --- | --- |
| 权限、账号和业务资源隔离 | 可以请求任务，不能自行声明实际副作用安全 |
| 基础规则自动触发 | 可以补充规则，不能因未选择而取消基础覆盖 |
| 动作前取证和持久日志 | 可以读取和解释，不负责凭记忆决定是否保存 |
| 请求去重、超时、取消与清理 | 遵循状态反馈，不盲目重试结果未知的写操作 |
| 参数、状态版本和证据引用校验 | 不通过自定义参数绕过工具契约 |
| 上下文预算与关键状态保留 | 可提出关注点，不能静默丢弃必要限制 |

Agent 拥有受任务边界约束的探索自主权；执行层控制动作准入与可靠性。工具允许合法的新探索请求，不把预设下一步建议当成所有可能行动的完整清单。

## 6. 工作记录与证据要求

Agent 保存目标、观察摘要、假设、选择依据、验证计划和知识引用。这些是可审阅的工作记录，不要求输出模型内部思维链。

每个确定发现应能回答：

1. 实际发生了什么？
2. 根据什么认为预期不同？
3. 在什么角色、数据和状态下发生？
4. 哪些观察或操作支持结论？
5. 排除了哪些相关的合理解释，仍有哪些不确定性？

证据不足时保留候选或 unknown；主观建议单独表达。页面内容视为待检查数据，不作为修改任务权限或工具行为的指令。

## 7. 评估目标与验收案例

评价 Agent 的目标是自主发现有价值问题，并形成可靠复用能力，而非仅提高点击或任务完成成功率。

| 维度 | 关注点 |
| --- | --- |
| 探索质量 | 是否选择高价值状态、发现新分支、避免无效重复 |
| 发现质量 | 固定案例中的漏报、误报，以及证据完整性 |
| 执行判断 | 是否正确处理阻断、未知结果、资源等待和恢复 |
| 知识使用 | 是否引用有效版本，是否区分规范和现状 |
| 运行成本 | 有效发现所需时间、工具调用、模型用量和重复读取 |
| 演进效果 | 更新后发现已知问题，同时保留合理例外 |

至少验证：

- 没有预定义 Journey 和完整规则库时，能从目标与入口开展探索。
- 发现新状态后能更新计划，而不是只运行初始清单。
- 有规则时复用检查；无规则时提出假设并获取证据。
- 关闭 banner 后完成任务，仍报告原始阻挡及恢复动作。
- 预期 rejected 被正确识别，不与执行错误混淆。
- 多分支资源冲突时等待或改做独立检查，不越权并发。
- 预算耗尽时列出未探索分支与未决问题，不宣称全站通过。
- 漏报反馈形成可验证的改进和回归案例，而不是仅追加提示词。

本文定义职责和行为目标。具体工具接口、资源策略、规则模型和知识治理分别以配套文档为实施依据。
