# 验证靶场库与持续评估设计

日期：2026-09-20  
状态：设计约定，尚未实现和实测  
范围：靶场案例、变体、评估答案、维护职责、候选入库、发布回归和成熟阶段的持续验证。

总体设计入口：[应用总体架构](./architecture.md)。配套：[Agent 职责](./agent-responsibilities.md)、[执行层](./execution-engine.md)、[规则库](./rules-and-rule-library.md)、[知识库](./knowledge-and-context.md)。

## 1. 定位

靶场库是一组可运行、可重置、有独立评估依据的测试应用与案例，用于验证 Agent 探索、规则检测、交互执行、证据采集和恢复能力。

它同时服务于开发验证、演示和持续发布评估，但用于调优或演示的案例不能再宣称是 Agent 从未见过的保留测试。

产品成熟后，模型、提示词、工具、知识和规则仍会变化。靶场持续检查这些变化是否改善能力，是否导致旧问题漏报、合理情况误报或运行成本异常。

靶场不替代真实应用验证。真实误报、漏报提供新案例，靶场提供可控复现和可比较的评估。

## 2. 案例组成

| 部分 | 内容 | 被测 Agent 是否可见 |
| --- | --- | --- |
| 可运行应用 | 页面、业务交互、测试数据、故障注入 | 通过正常页面与授权工具访问 |
| 检查任务 | 用户目标、入口、允许操作、正常业务要求 | 可见 |
| 评估答案 | 实际缺陷、合理例外、预期结果和触发条件 | 不可见 |
| 评估器 | 验证案例有效性、结果匹配和证据要求 | 不可见 |
| 运行清单 | 修订、变体、随机种子、环境和重置方案 | Agent 只获得执行所需信息 |

建议开发目录：

```text
arena/
  checkout-overlay/
    app/
    variants/
    fixtures/
    task.yaml
    evaluator/
```

目录分开不是权限隔离。正式评估时，私有答案、故障配置、评估器及泄露答案的源码不得挂载到被测 Agent 的文件系统、知识索引或可访问接口。测试控制端可以知道当前变体，任务端只获得正常用户任务。

不在 URL、任务标题或页面提示中泄露故障名称。故障注入入口与正常业务入口分离。源码辅助模式若被测试，需另设明确评估协议，不让隐藏答案通过源码访问泄露。

## 3. 测试类别与变体

### 3.1 已知规则检测

验证已有能力：遮挡、长文本溢出、输入丢失、操作反馈、配置时间预算等。答案明确列出适用规则和预期证据，但这些答案不进入被测上下文。

### 3.2 合理行为辨别

包括预期支付拒绝、必要验证步骤、明确自动保存以及已授权的局部设计例外。不能只有故障页面，否则到处报错也可能获得高分。

### 3.3 无对应规则的探索

固定本轮可用规则清单，排除与目标异常等价的直接检测规则，让 Agent 根据任务、产品要求和实际行为提出假设并验证。

正常产品要求可提供；具体故障位置、触发答案和评估断言不可提供。记录模型、提示词、可用知识与规则版本。移除一条规则不证明案例绝对新颖，开发集与保留集隔离仍然必要。

### 3.4 执行可靠性

注入浏览器断连、延迟、任务取消、服务重启、资源竞争和写操作结果不明等故障，检查是否重复提交、丢失证据或错误释放资源。

### 3.5 变体生成

同一案例可以改变文案、语言、位置、DOM、视口、内容长度、触发时间、角色和数据状态。记录种子、构建修订和 fixture；仅记录随机种子不足以保证复现。

变体必须通过独立有效性检查，确认目标问题仍存在、正常行为仍正常。随机改布局后原缺陷消失的变体不能继续作为漏报答案。

## 4. 维护职责

| 角色 | 负责 | 不允许 |
| --- | --- | --- |
| 开发团队 | 靶场框架、初始案例、重置机制、评估器、隔离和发布门槛 | 以一次成功演示代替回归证据 |
| 应用 Agent | 从真实探索和反馈提出候选，整理证据、复现条件和原因 | 直接修改正式答案或发布评估集来提高自身得分 |
| 案例构建任务 | 在隔离环境生成最小复现及正反变体 | 接触不必要的客户资料或直接操作生产环境 |
| 独立评审与评估流程 | 核验案例、确定预期、批准入库和评分 | 将被测 Agent 的自述当作唯一正确性依据 |

案例构建与被测运行分离。构建任务可由开发者或专门 Agent 执行；应有独立工作目录、权限、输入与产物，不是正在检查用户应用的 Agent 随手修改正式测试。

独立评估首先依赖确定性断言和已确认规范。模型可以辅助审阅语义问题，但不能仅因换了一个 Agent 就宣称评估客观；有歧义的新业务预期需要人工判定，记录理由。

## 5. 候选案例入库

```text
真实发现 / 人工误报或漏报反馈
  → 脱敏并整理触发条件与证据
  → 创建案例构建任务
  → 生成最小复现与合理对照
  → 独立验证案例有效性
  → 审核预期与适用范围
  → 发布不可变案例修订
  → 按用途进入开发集或评估集
```

先验证“案例确实复现了问题”，再测试“Agent 是否发现”。如果案例条件未成立，本轮记为 invalid / infrastructure-error，不能记为 Agent 漏报或通过；同时保留并报告失效次数，避免通过排除失败运行美化结果。

### 5.1 入库门槛

- 已有规范的机械变体：有效性自动验证通过后，可进入开发集。
- 新业务行为、新问题类型：核对预期与正反案例，明确规则依据后入库。
- 发布评估集：经审阅、固定版本、答案隔离，限制访问和修改。
- 无法脱敏或不能可靠复现：保留为受限历史案例，不伪装成可重复靶场。

案例状态可采用 proposed、validated、approved、published、retired，记录构建者、评审者、来源和替代修订。修改答案产生新版本，并说明旧分数是否仍可比较。

## 6. 评估数据和运行流程

单个案例至少定义：caseId/revision、应用构建、fixture、变体种子、Agent 可见任务、预期业务结果、私有缺陷集合、合理例外、允许副作用、预算、重置方法和评估器版本。

每次评估流程：

1. 准备隔离环境，重置业务数据。
2. 独立检查目标状态和故障条件有效。
3. 固定模型、提示词、知识、规则、工具及运行配置。
4. 向 Agent 提供正常任务，不提供故障答案。
5. 执行并保存动作、模型调用、事件和证据。
6. 评估器核对发现、执行轨迹、业务终态和副作用。
7. 输出分项分数、失败归因和案例有效性。
8. 清理或隔离残留状态，防止污染下一轮。

对非确定性的 Agent 重复运行，报告次数、成功分布和波动，不选择性展示最好的一次。比较两个版本时尽量固定案例条件和预算；任何变化都进入运行清单。

## 7. 评分维度

| 维度 | 判断内容 |
| --- | --- |
| 发现 | 已知缺陷是否报告；合理行为是否误报；重复问题是否正确聚合 |
| 证据 | 截图、测量和操作是否支持结论，是否来自正确状态 |
| 探索 | 是否到达触发状态，是否区分未探索和已检查 |
| 执行 | 是否越界、重复写入、提前恢复或跳过必要验证 |
| 恢复 | 取消、断连、重启后的状态核对与资源处理 |
| 成本 | 总耗时、模型用量、无效动作与重试 |

发现匹配依据是缺陷对象、触发条件和事实，不只匹配报告关键词。未在已知答案中的新发现单独进入评审，不能未经核验一律判误报，也不能由 Agent 自行算作命中。

证据质量与发现率分开报告。只有一句“存在遮挡”但没有关闭前现场，不应与完整证据同等计分。

典型否决项：测试要求检查原始阻挡，Agent 关闭 banner 后完成任务，却未记录原始问题。任务完成不能抵消该检查失败。重复提交、越权等执行错误单独列出，不被高发现率掩盖。

## 8. 开发集、回归集与保留集

| 集合 | 用途 | 管理要求 |
| --- | --- | --- |
| 开发集 | 调提示词、工具、规则和案例构建 | 允许反复查看与调优 |
| 稳定回归集 | 检查已知能力是否退化 | 固定答案和版本，可包含已用于学习的案例 |
| 保留评估集 | 检查对未参与调优案例的泛化 | 隔离答案及直接泄露答案的材料，控制访问 |

按案例家族而非仅随机种子划分，避免同一缺陷模板的近似变体同时充当训练材料和“全新”评估证据。发布结果注明可用知识，不混淆是否提供该缺陷的历史案例或规则。

保留案例一旦用于针对性调优，应转为已见案例或回归集，并补充新的保留案例。测试时默认禁止将私有答案或评估反馈写入被测知识库；运行生成的学习产物隔离保存，评估结束后再按协议处理。

## 9. 成熟阶段的持续用途

- 发布回归：规则、工具、执行器或知识更新后，检查旧问题是否复发。
- 模型与成本选型：比较便宜或更快模型是否损失关键发现能力。
- 规则与例外验证：检查新规则误伤和例外范围过宽。
- 故障恢复：持续验证崩溃、取消、重启与未知副作用处理。
- 真实事故复盘：将确认漏报转为以后的稳定回归案例。

按变更风险选择测试范围：局部规则修改先跑相关正反集合，模型、工具契约或执行内核变化跑更广的集合。发布门槛由项目明确配置，不能在结果不佳时由被测 Agent 自行放宽。

靶场需要持续补充新案例、变体和真实问题；静态高分不能证明在真实应用中持续有效。

## 10. 最小落地范围

实施顺序、首批案例及验收门槛见[最小可验证路径开发计划](../plans/minimum-validation-plan.md)。

先建立一个购买靶场，包含：正常下单、可关闭遮挡、不可关闭遮挡、按钮改名/移位、预期拒绝，以及没有对应规则的恢复异常。

实现重置、答案隔离、证据验证和版本记录后，再扩展案例数量。案例库与产品使用同一套正式执行入口，不能通过评估专用捷径绕过工具校验或取证。

最小闭环：用户提交购买检查 → Agent 探索 → 输出真实问题及证据 → 独立评估 → 人工确认 → 生成规则候选 → 正反案例验证 → 下一次稳定复查。

## 11. 验收要求

1. 被测 Agent 无法读取私有答案、故障配置和评估器。
2. 正常与异常变体均可重置、复现并被独立核验。
3. 无规则异常可以通过探索验证，规则清单及知识版本可追溯。
4. 能区分无效案例、执行错误、漏报、误报和证据不足。
5. Agent 完成业务任务但漏掉质量问题时不会获得完整通过。
6. 候选构建者不能绕过评审修改正式答案或发布门槛。
7. 案例构建、被测运行和评估记录拥有明确权限边界。
8. 已用于调优的案例不再被宣传为未见测试。
9. 重复运行的波动、成本和失效次数完整报告。
10. 真实漏报可以进入脱敏复现、审阅和持续回归闭环。

本文定义持续验证机制，不代表已有靶场实现，也不新增第三方框架依赖。
