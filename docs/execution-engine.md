## 1. 技术决定与职责边界

执行层采用 TypeScript、Mastra、Playwright 和 Midscene.js。

本应用以 Agent 为检查主体，不要求人预先穷举页面、路径和规则。Agent 根据目标理解页面、持续规划探索、提出新问题并验证；执行层与规则库用于提速、保证一致性、节约 token 和保留证据。Agent 不是只在脚本失败后工作的补救机制。

| 模块 | 职责 |
| --- | --- |
| Agent 探索规划器 | 理解目标和页面、维护探索状态图、安排验证、更新优先级 |
| Journey / Scenario | 业务路径、场景条件、步骤和合法分支 |
| 自有调度器 | 任务图、预算、账号分配、资源冲突和执行顺序 |
| Mastra | Agent、工具、工作流、Server、存储接入与追踪能力 |
| Playwright | 浏览器操作、DOM/CSS 采集、状态观察、截图和执行证据 |
| Midscene.js | 动态目标的视觉定位、语义和视觉判断补充 |
| 自有规则引擎 | 按规则判断事实，记录问题与覆盖情况 |
| 持久化与证据存储 | 任务、检查点、事件、截图、报告及版本信息 |

Mastra 是 Agent Server 底座。优先复用框架的模型交互、工具、工作流状态、暂停恢复和追踪；项目实现账号与业务资源调度、浏览器恢复、规则和证据等领域能力。规则作者继续使用声明式模板或访问器，不必直接依赖框架运行时。

## 2. 核心执行流程

```text
用户目标与入口（可选 PRD、Journey）
  → 创建 Run 并固定配置
  → Agent 观察、更新探索图、选择探索或复用已有路径
  → 生成有边界的任务和验证计划
  → 准备场景和数据
  → 分配账号及业务资源
  → 创建浏览器上下文并恢复检查点
  → 验证前置条件
  → 定位当前动作目标
  → 保存动作前现场
  → 执行动作前规则
  → 执行必要的准备动作和业务动作
  → 等待后置条件或超时
  → 保存结果状态并执行相关规则
  → 更新探索图和假设状态
  → 选择已知合法分支，或规划新的受约束探索任务
  → 根据完成条件、阻断或预算继续或结束
  → 保存终态，清理并释放资源
```

单个任务和动作的执行是受控状态机，整体探索计划由 Agent 动态扩展。已定义 Journey 按已知分支执行；未预定义路径允许 Agent 发现新状态和动作，但不能跳过资源策略、取证和后置条件验证。新观察不自动修改已确认业务预期，也不能以一句“操作成功”替代证据。

### 2.1 模块划分

- 探索规划器：维护状态图、待探索分支和优先级，决定复用规则或启动新假设验证。
- 假设管理器：记录候选问题、验证计划、支持或反驳证据和规则沉淀建议。
- 场景执行器：读取路径定义，控制步骤、分支、前置条件、后置条件和终止。
- 目标解析器：将业务意图映射到当前目标，输出定位方法、歧义和证据。
- 观察器：生成带时间和环境信息的页面事实快照。
- 规则调度器：依据事件和事实选择检查，复用采集结果。
- 动作执行器：统一执行点击、输入、滚动、关闭、重试等改变状态的动作。
- 轨迹记录器：持久保存事件、版本、证据引用和运行结果。

### 2.2 探索状态图与停止条件

状态图是探索过程中逐步建立的记录，不预先声称完整。节点标识页面及相关业务状态，边记录动作及观察到的转换。URL 相同但弹窗、表单、权限或业务反馈不同，可能属于不同状态。

每个状态关联快照、角色、fixture、入口、已检查事项和未知项；每条分支记录 discovered、queued、exploring、explored、blocked 或 deferred，以及原因。visited 不代表所有交互和规则都已检查。

Agent 根据业务重要性、近期变化、未知程度、预期信息收益和预算决定优先级，保存简短依据。引擎通过状态指纹和访问记录辅助去重，动态数据差异不必全部扩展为新任务；合并不确定时保留差异，避免错误去重漏掉状态。

并行分支共享持久探索记录，任务通过领取机制避免无意重复探索；刻意复现或不同视口验证允许重复，但需声明目的。

停止原因包括目标已满足、已知待探索队列为空、预算耗尽、权限或环境阻断、人工取消。队列为空只说明当前已发现范围内没有待办，不证明应用所有状态已覆盖。

### 2.3 假设与验证循环

```text
观察到新现象
  → 提出可证伪的问题假设
  → 明确预期依据、验证动作和所需证据
  → 复用已有规则，或组合底层能力验证
  → supported / refuted / inconclusive
  → 报告发现、继续调查或关闭假设
```

假设至少包含现象、依据、scope、验证计划和证据引用。没有规则时可直接验证并报告，但最终确定性结论仍需充分证据。主观改进意见作为 suggestion 单独展示。

验证计划只能使用受控工具和已授权动作。没有规则不等于允许执行任意代码或绕过资源调度。需要新检测能力时提出扩展请求，而不是伪造测量结果。

规则不是报告前置条件。确认后的模式可提议为规则、Journey、语义映射或探索策略；这些产物的发布与本次发现报告分开。

## 3. Run 与原子任务

### 3.1 Run

```ts
interface RunSpec {
  goal: string;
  entryUrls: string[];
  mode: "explore" | "journey" | "hybrid";
  journeyId?: string;
  caseId?: string;
  environment: string;
  actorRequirement: string;
  viewport: { width: number; height: number };
  ruleProfile: string;
  limits: {
    totalMs: number;
    maxActions: number;
    maxModelCalls: number;
  };
}
```

运行开始时锁定路径、规则、例外和配置版本。具体账号由调度器选择，必须满足角色、权限和数据条件。

存在 Journey 时固定其版本；探索模式无需预先存在 Journey 或 case。执行中新增探索计划和验证谓词保留修订记录，不静默改写已有预期。模式约束通过运行时 schema 验证，例如 journey 模式必须提供有效 journeyId。

### 3.2 原子任务的边界

任务单位是一段可验证的状态转换，例如“提交登录并确认进入已登录状态”。每次键盘输入不必独立成为调度任务，但动作仍需要记录。

```ts
interface TaskSpec {
  id: string;
  parentTaskId?: string;
  checkpointId: string;
  goal: string;
  explorationNodeId?: string;
  hypothesisId?: string;
  precondition: string;
  completionCondition: string;
  mode: "snapshot-read" | "browser-interaction";
  effects: {
    reads: string[];
    writes: string[];
    session: "preserve" | "invalidate" | "unknown";
  };
  limits: {
    timeoutMs: number;
    maxActions: number;
    maxModelCalls: number;
  };
}
```

每个任务定义输入、完成条件、资源影响、输出证据、重试策略和清理责任。“原子”表示边界清晰，不保证外部系统事务性或自动回滚。

## 4. 动作协议与目标解析

### 4.1 定位与操作分离

定位顺序：已确认映射 → 当前 DOM 信息 → Midscene 视觉补充。缓存命中仍需验证上下文，不能因 selector 还能匹配就默认业务身份没有变化。

解析返回 resolved、ambiguous 或 not-found，以及目标引用、定位方式和证据。定位请求不允许隐式关闭 banner 或点击目标。

如需滚动才能观察更多内容，该滚动由动作执行器显式执行，记录原因及前后视口。

### 4.2 动作前后检查

在底层自动滚动或恢复操作之前保存原始状态，执行 before-action 检查。动作发出后，依据可观察谓词等待反馈；after-action 事件不等于业务步骤已经完成。

同一批规则读取一致快照。页面变化后生成新快照；跨时刻的截图、样式和命中测试不得作为同一瞬间的确定事实。

### 4.3 重试和取消

- 只读采集可以依据错误类型有限重试。
- 提交订单等写操作结果不明时，先核对业务状态，不能直接重复提交。
- 取消调度不等于撤销已发出的请求。
- 任务取消信号需要与底层调用的取消、超时或上下文关闭适配；包装 Promise 不保证浏览器动作已停止。
- 副作用状态未知时，任务进入待核对状态，对冲突资源保持隔离，不能立即当作干净资源再次分配。

## 5. 检查点与登录复用

```ts
interface Checkpoint {
  id: string;
  parentId?: string;
  actorRef: string;
  sessionStateRef: string;
  entryUrl: string;
  readinessCondition: string;
  snapshotRef: string;
  fixtureRef: string;
  restorePlanRef?: string;
}
```

检查点包含可恢复会话的安全引用、入口、验证条件、事实快照、测试数据条件和必要恢复计划。不将凭据直接写入日志或传递给模型。

恢复流程：创建独立上下文 → 注入可恢复会话状态 → 进入入口 → 执行恢复计划 → 验证登录和数据条件。

这不是浏览器内存克隆。页面内存、正在执行的请求、临时 UI 状态和服务端数据不会自动复制。应用可能还依赖额外存储或会话规则，需要应用级适配。恢复验证失败时，不得把子任务标记为已经到达检查点。

共享账号发生业务数据变更后，旧检查点仍可保留为历史证据，但其恢复条件可能已失效。后续任务重新验证并准备数据，不声称自动回到了旧状态。

## 6. 分叉、并发和账号资源池

### 6.1 创建任务与开始执行分离

AI 可以提出 spawn 请求，调度器决定何时执行：

```ts
spawn({
  from: "authenticated-home",
  task: "检查购物车修改",
  isolation: "auto",
});
```

auto 表示由资源策略判定，不表示由模型猜测可以安全并行。每个子任务获得目标、检查点、规则配置和必要证据摘要，不复制父任务的完整对话。

```text
登录前快照 ── 布局规则、文本规则并行
登录任务
  → 登录验证完成，创建检查点
      ├─ 个人资料只读检查
      ├─ 导航交互检查
      ├─ 购物车修改：申请资源后执行
      └─ 退出登录：等待账号相关任务结束
```

### 6.2 两种并行

- 快照并行：多个规则共享不可变快照，不创建额外浏览器。
- 交互并行：每个分支拥有独立浏览器上下文，且服务端资源影响不冲突。

框架子任务或并行步骤不等于操作系统进程，也不提供独立浏览器或 CPU 并行。进程内任务使用受控并发；重计算或需要故障隔离的执行通过 worker/进程池承担。

### 6.3 账号少时的资源策略

| 任务影响 | 调度方式 |
| --- | --- |
| 读取同一不可变快照 | 直接并行 |
| 只改变独立浏览器内状态 | 独立上下文并行 |
| 读取服务端资源 | 允许共享读，不与写任务冲突 |
| 修改同一服务端资源 | 申请独占资源，冲突则等待 |
| 使账号会话失效 | 对账号及相关会话排他执行 |
| 副作用不明确 | 默认独占账号；可能影响共享组织等范围时扩大隔离或暂停确认 |

资源示例：account:A:cart、account:A:session、order:123、product:456:inventory、organization:789:settings。

两个不同账号仍可能修改同一库存或组织配置，因此账号数不是隔离正确性的保证。会话排他锁需要与该账号全部相关任务冲突，不能仅靠不同字符串的独立 mutex 实现层级冲突。

### 6.4 调度流程

1. 选择满足角色、权限和数据要求的账号。
2. 按资源层级和读写关系申请完整的已知资源集合。
3. 获取资源后，重新验证检查点和前置条件。
4. 执行任务并持续检查实际影响范围。
5. 发现新增资源需求时暂停，按统一锁策略重新调度，避免持有部分资源无限等待。
6. 清理、核对副作用和数据状态，释放资源。

采用确定的资源获取顺序或原子资源集合申请避免死锁；设置等待预算和公平策略。锁只协调本执行系统内的任务，无法阻止真实用户或其他系统修改数据，因此优先使用隔离测试数据并验证关键前置状态。

## 7. Mastra 集成

### 7.1 Agent、工具与工作流

- Mastra Agent 承担动态探索、模型决策与工具循环，不要求预先定义所有页面路径。
- Tools 将现有工具契约包装为框架工具，复用参数校验、上下文和追踪接入，领域权限与资源校验仍由项目执行。
- Workflows 承担已明确的执行协议和可复用流程，例如环境准备、检查点验证、检查与结果保存；可以调用 Agent，但不将所有未知探索强制改写为固定步骤。
- Server 暴露 Agent、工作流和自定义业务 API。产品 Web 工作台单独实现；Studio 用于开发调试，不替代客户报告界面。

不维护另一套平行的模型工具循环。模型适配以 Mastra 为入口；浏览器动作只经领域工具执行。

### 7.2 领域任务接口

```ts
type TaskOutcome =
  | { status: "completed"; result: TaskResult }
  | { status: "blocked"; reason: string }
  | { status: "cancelled" }
  | { status: "execution-error"; error: ExecutionError };

type TaskHandler = (
  spec: TaskSpec,
  context: { signal: AbortSignal; services: TaskServices }
) => Promise<TaskOutcome>;
```

这些是项目接口示意，不是 Mastra 原生类型。TaskResult 可以包含产品违规和预期业务拒绝；ExecutionError 表示浏览器断连、恢复失败、存储失败等执行错误。TaskServices 提供浏览器、资源调度、检查点和证据存储。

规则 fail 不作为工作流异常抛出。独立分支的执行错误在任务边界形成可汇总终态；只有共享前提失效等明确条件触发组级取消。流程节点可因基础设施错误失败，但不能用这个通道表达普通产品问题。

### 7.3 能力归属与状态来源

| 能力 | 归属 |
| --- | --- |
| 模型调用、Agent 工具循环 | Mastra Agent |
| 工具 schema、框架上下文和调用追踪 | Mastra Tools 接入项目工具契约 |
| 工作流状态、暂停与恢复 | Mastra Workflows，配置并验证实际存储与 runner |
| HTTP API 与流式返回 | Mastra Server，可经 Server Adapter 扩展 |
| 开发调试与框架追踪 | Mastra Studio / tracing |
| 账号与业务资源冲突、子任务预算 | 项目领域调度器 |
| 浏览器上下文、登录复用、业务状态核对 | 项目浏览器与检查点服务 |
| 规则、快照、发现、覆盖和原始证据 | 项目质量检查服务 |

框架工作流实例以其运行记录为准；项目任务记录保存领域状态并关联 frameworkRunId，不自行复制第二套工作流指令位置。框架快照存放可序列化数据和引用，不存活浏览器句柄。

明确区分框架执行快照与浏览器检查点：前者用于恢复编排，后者用于重新到达并验证应用状态。恢复工作流不会自动恢复浏览器或外部业务数据。

会话 Memory 服务于 Agent 交互，不替代有来源、修订和范围的产品知识库。追踪日志也不替代必须持久保存的证据与业务事件。

### 7.4 资源生命周期与持久执行边界

使用显式资源获取/释放、try/finally、取消信号及 worker 清理协议管理浏览器与锁。每个工具适配器验证底层是否支持中止；不支持时通过超时、关闭上下文和业务状态核对处理。进程崩溃时由外部回收与恢复核对兜底，不能保证 finally 一定执行。

- 暂停/恢复能力不等于任意崩溃点均无损恢复，需核验快照时机、存储和 runner 语义。
- 多步骤并行不自动解决跨机器任务分配与账号/业务资源锁。
- 恢复可能重新进入执行逻辑；写操作需请求去重、结果核对及适用的幂等机制。
- 取消任务不撤销远端副作用；状态未知时保持隔离并核对。
- 浏览器、模型调用和账号分别设并发与预算，分叉不突破父任务约束。

优先复用 Mastra 提供的存储与 workflow runner 接口，避免重复开发通用编排引擎。具体持久化后端、多机器 runner 与共享资源协调机制仍需选型和故障测试，不能假定引入框架即可获得全部分布式保证。

## 8. 结果模型与报告

运行报告分开显示三类结果：

| 维度 | 示例 |
| --- | --- |
| 业务结果 | success、rejected、尚未取得结果 |
| 执行状态 | completed、blocked、timed-out、cancelled、execution-error |
| 检查结果 | pass、fail、unknown、skip、error，按对象统计 |

例如“下单成功，发现 1 个错误和 2 个警告，另有 1 项无法判断”。恢复成功不能抹去原始问题。

默认交付：运行概览、问题证据卡、执行时间线，以及机器可读 JSON。报告包括计划和实际覆盖、未执行原因、规则版本、环境及视口。

报告同时包含探索覆盖和规则覆盖，列出未探索入口/状态、未决假设与停止原因。探索发现以 hypothesisId 和验证记录关联，不强制存在 ruleId。报告区分候选、有证据的发现、无法判断和主观建议；预算内未发现问题不能描述成整个应用无问题。

问题卡至少展示规则、发生步骤、预期、实际、影响、证据、复现条件和恢复记录。截图采集失败时标明证据不完整，不删除已有可靠发现。

## 9. 截图与标注

### 9.1 采集时机

1. 动作前保存原始状态。
2. 异常出现时保存现场。
3. 自动恢复前确认原始证据已保留。
4. 恢复后保存对照。

原始视口截图优先用于“按钮在屏幕外”等问题；全页截图是补充，不能替代用户当时可见的视口。

### 9.2 标注生成

标注是基于坐标的确定性后处理，不使用生成式图像改写现场。保留未标注原图，并生成独立副本。

- DOM 边界可靠时，画出目标和遮挡元素范围。
- 仅视觉识别时，标明区域属于估计。
- 目标完全不可见且没有其他位置依据时，只标出浮层，不编造目标边界。

标注关联快照 ID、视口、滚动偏移、设备像素比例和截图缩放。处理 iframe 等坐标转换；截图与几何采样不一致时重采集或降低结论确定性。

几何重叠不是指针阻挡的充分证据。截图与命中测试、状态变化等信息共同支持结论。

### 9.3 不同问题的证据

| 问题 | 证据 |
| --- | --- |
| 字号、间距 | 元素截图、实际和预期值 |
| 遮挡、溢出 | 原始视口、布局信息、命中测试 |
| 错误后丢失输入 | 前后截图与字段状态差异 |
| 非预期 rejected | 业务条件、原因反馈与终态证据 |
| 超过时间预算 | 起止事件、测量误差、等待状态和结果截图 |
| 执行器错误 | 最后现场、异常类型和未完成项 |

## 10. 执行日志与复盘

记录可验证的观察、输入输出、简短决策依据和动作，不记录或要求模型内部思维链。

| 类别 | 内容 |
| --- | --- |
| 观察 | 截图/快照引用、已知事实和缺失项 |
| 规则选择 | 候选、选中、排除、延期及依据 |
| AI 调用 | 指令和模板版本、输入证据引用、结构化输出、模型版本、耗时和用量 |
| 动作 | 目标、定位方式、准备动作、业务动作和恢复动作 |
| 判定 | 规则版本、参数、实际值、预期值及结果 |
| 调度 | 分支父子关系、账号分配、资源等待和取消 |
| 探索 | 状态图变更、候选分支、选择依据、去重和停止原因 |
| 假设验证 | 假设版本、预期依据、验证动作、支持和反驳证据 |

事件至少关联 runId、taskId、stepId、actionId、snapshotId 中适用的字段，以及事件 ID、版本和时间。并发事件使用因果引用和分支内顺序，不只依靠墙上时钟推断先后关系。

典型事件包括 task.spawned、resource.waiting、checkpoint.restored、target.resolved、snapshot.captured、rule.completed、action.dispatched、state.changed、finding.created、task.completed。

面向用户展示简洁时间线；复盘视图展开事实来源、规则选择、模型输入输出和成本。截图和 DOM 独立存储，通过引用避免重复。

## 11. 漏报反馈与演进

用户对某次运行提交漏报，指向步骤、时间或截图区域。系统按以下链路分析：

```text
未到达状态？
  → 场景覆盖
到达但未采集？
  → 观察时机与采集器
采集到但未选规则？
  → 路由与检索
执行规则但判断错误？
  → 规则、语义识别与参数
恢复动作提前掩盖现场？
  → 执行顺序
生成问题但报告丢失？
  → 聚合与展示
```

改进流程：关联现场 → 提出有证据的原因 → 生成修改建议 → 加入回归案例 → 验证修复与误报情况 → 发布版本。

还需区分“未发现入口/未规划探索”与“已有场景执行失败”。改进对象包括探索策略和状态识别，不能将所有漏报都归因于缺少规则。新路径、页面知识与验证案例同样是可积累资产。

快照足够时离线重跑规则；涉及动作、服务端状态或时序时重新准备环境并复现。日志不保证完整重放真实世界，也不能证明未被指出的遗漏不存在。

## 12. 数据保护与保留

会话状态属于敏感数据，检查点保存受控引用。日志和模型输入不包含密码、令牌等秘密；截图和表单值按项目配置脱敏。明确证据保留周期和访问权限。

脱敏影响判断时记录缺失事实，不能把不可见数据假设为正确。关键执行事件与问题证据需要可靠持久化，不能因调试日志采样被丢弃。

## 13. Agent 接入与工具契约

### 13.1 工作模式

本应用以 Agent 为检查主体和用户入口。用户提供目标、资料和测试环境，Agent 自主理解页面、规划探索、提出假设、选择检查、验证并报告；执行层通过工具服务承接请求。完整 PRD、Journey 和规则集不是启动探索的前提。用户不需要手动调用浏览器程序。

```text
用户目标 / PRD / 规则配置
  → 主 Agent：维护探索计划、创建任务、分配预算、汇总结果
  → 任务 Agent：理解页面、提出并验证假设、扩展状态图
  → 工具服务：校验请求、绑定上下文和权限
  → Mastra Agent / Workflow 调用领域工具：调度、操作、检查、持久化
  → 结构化结果和证据引用
```

主 Agent 与任务 Agent 是职责区分，不强制采用不同模型或进程。确定性检查直接运行代码，不为每个规则创建模型会话。

Agent 发起有业务意义的任务；资源管理、动作前检查、取证和持久日志自动执行，不能依赖模型记得逐一调用。基础规则不可因 Agent 未显式选择而被跳过。

### 13.2 工具集合与职责

统一使用 page.observe、page.act 命名页面工具，不再并列暴露职责相同的 browser.observe、browser.act 别名。下表为设计接口，尚未实现。

| 工具 | 用途 | 边界 |
| --- | --- | --- |
| rules.search | 按目标、页面类型和事实检索规则清单 | 返回元数据；不执行规则，不加载全部脚本给模型 |
| exploration.update | 登记入口、状态、分支、优先级与停止原因 | 以证据关联图节点，版本化更新；不因访问一次标记全面完成 |
| hypotheses.record | 创建或修订候选问题及验证计划 | 保存简短依据，不把假设直接标为违规 |
| findings.submit | 提交探索发现或建议，关联验证记录和证据 | 无需 ruleId；校验证据引用和状态，不能仅凭模型宣称升级为确定违规 |
| knowledge.propose | 提议规则、路径、语义映射或探索策略 | 生成待审阅产物，不直接改写有效规范 |
| page.observe | 观察当前页面、目标区域或指定事实 | 不主动改变页面，不隐式滚动或关闭浮层 |
| page.act | 执行一个明确的业务动作 | 自动取证和检查；受权限、资源和恢复策略约束 |
| checks.run | 在当前状态运行指定或自动匹配的规则 | 不操作页面；缺少状态时返回未完成原因 |
| checkpoints.create | 验证并保存可复用状态 | 必须验证恢复条件；不提供内存克隆承诺 |
| tasks.spawn | 从检查点创建任务或子任务 | 立即返回任务 ID 和调度状态；不保证立即并行 |
| tasks.wait | 等待任务完成、阻断或需要决策等重要变化 | 有界等待，支持事件游标，避免重复返回历史 |
| tasks.inspect | 获取任务摘要、指定日志或证据 | 默认摘要，按需展开；不能替代浏览器实时观察 |
| tasks.cancel | 请求取消任务及其可取消操作 | 不表示撤销已发生的业务副作用 |

page.observe 是协议上的只读操作，但页面自身仍可能动态变化或产生后台请求；其观察结果必须标注快照与状态版本。

### 13.3 每个工具的说明模板

工具说明统一包含：用途、调用条件、副作用、参数约束、返回状态、后续处理和最小示例。避免“操作浏览器”等无法区分职责的描述。

page.act 的说明示例：

> 在当前任务中执行一个业务动作。适用于动作意图明确的情况。执行前自动保存现场并运行适用规则。遇到当前策略未允许的恢复动作时返回 blocked，不擅自关闭浮层。返回动作是否实际发出，以及后置条件是否成立。

工具清单不暴露工作流内部句柄、锁句柄、BrowserContext 和数据库连接等实现细节。可按主任务与子任务角色提供不同工具权限，但保持统一语义。

### 13.4 参数设计与上下文绑定

自由文本用于表达意图；已有路径的结果条件、资源引用和状态应使用结构化定义。

```json
{
  "intent": "提交当前订单",
  "expectedOutcomeIds": ["payment-required", "order-rejected"]
}
```

expectedOutcomeIds 必须来自当前 Journey 的有效定义，不能由模型临时编造。探索任务没有预定义终态时，可以省略该字段，工具返回实际观察事实。Agent 可通过 hypotheses.record 定义版本化验证计划；其预期必须标明是规范依据还是待验证推测，不能把观察到的行为直接宣布为业务正确。

任务 ID、账号、浏览器上下文和权限由可信工具会话绑定；跨任务操作需要显式 ID 并验证访问范围。schema 拒绝未知字段、无效枚举和越权资源。

状态敏感动作携带或绑定最近观察的 stateVersion。执行前重新检查有关事实；版本检查只是降低使用过期信息的风险，不能保证动态网页完全不变。

副作用和只读属性由工具实现与动作适配器确定。模型不能通过填写 readonly 等参数改变实际权限。子任务继承父任务限制，不能自行扩大账号权限或模型预算。

### 13.5 结构化返回与下一步提示

工具返回稳定的公共字段和各工具自己的类型化数据。以下为尚未发出动作的阻挡结果：

```json
{
  "status": "blocked",
  "actionDispatched": false,
  "stateVersion": 12,
  "summary": "活动浮层阻挡了提交订单按钮",
  "findingIds": ["finding-17"],
  "evidenceRefs": ["snapshot-42"],
  "nextActions": [
    {
      "tool": "page.observe",
      "arguments": { "focus": "阻挡提交操作的活动浮层" }
    }
  ]
}
```

page.act 返回是否发出动作和后置条件的判定。崩溃恢复等情况下无法确定是否发出，应显式标为 unknown，不将未知压成 false。业务结果、执行状态和规则结论仍按第 8 节分开记录。

findingIds 表示问题已由系统持久记录，不依赖模型再次描述才能保存。工具默认返回摘要和引用，详细 DOM、截图、规则日志按需获取。

nextActions 由可信执行逻辑根据当前权限和状态生成，并再次通过正常工具校验。它是合法后续操作的建议，不是绕过策略的授权。网页文字仅作为待检查数据，不能直接转化为工具指令。

blocked 或 needs-decision 通常表示需要 Agent 判断，不自动转为向用户确认。已有任务策略允许恢复时，Agent 可以继续；缺少必要授权或关键条件时再报告给用户。

### 13.6 可恢复错误

| 情况 | 返回与处理 |
| --- | --- |
| 定位或观察过期 | 返回 stale-state，要求重新观察相关区域 |
| 资源尚未就绪 | 返回 queued 和任务 ID，指向 tasks.wait |
| 目标有歧义 | 返回有限候选、区别与证据，请求进一步观察或选择 |
| 上次写操作结果未知 | 返回 outcome-unknown，先核对业务状态，禁止直接重提 |
| 超出权限或任务范围 | 返回 policy-denied，说明受限动作及允许的下一步 |
| 工具参数无效 | 返回字段级 schema 错误，不启动副作用 |
| 证据或模型预算不足 | 明确标注未完成范围，不伪装为检查通过 |

传输或格式错误与业务执行错误分开。重试保持同一逻辑请求 ID；同 ID 不同参数必须拒绝。请求 ID 在可信客户端/运行时创建并持久化，避免模型每次重试随意生成新 ID。内部去重不等于外部系统 exactly-once；写操作结果不明仍需状态核对。

### 13.7 分叉与等待协议

tasks.spawn 返回每个子任务的 ID、父任务关系、检查点及 running/queued 等状态。子任务只有在资源准入和恢复验证完成后才能开始浏览器动作。

tasks.wait 接收任务集合、事件游标和最大等待时长，返回新增的重要事件及最新游标。超时仅表示等待窗口结束，不表示任务失败。Agent 不应通过高频 inspect 轮询占用上下文。

完成检查点创建和持久保存后，才允许后续分支引用该检查点。主 Agent 使用结果摘要汇总，必要时读取证据；不把所有子任务原始对话灌入父上下文。

### 13.8 Agent 执行协议与案例

提供一份短协议：

```text
理解目标并观察当前状态
  → 更新探索图，选择入口、状态或待验证假设
  → 复用已有规则，或组合观察与动作完成新验证
  → 保存证据和发现，更新未知项
  → 根据结果继续、分叉、等待或记录停止原因
```

规则检索无结果时不结束探索。工具集提供的建议动作是合法候选，不是穷举清单；Agent 可以提出其他符合权限和任务边界的探索请求，由同一执行校验处理。

随工具契约维护正常通过、banner 阻挡、目标改名、资源等待、提交结果不明和任务取消等端到端示例。示例解释工具选择，不要求模型输出内部思维链。

重点评估工具选择正确率、参数错误率、重复调用、过期引用使用、错误重提、取证前恢复、调用次数和 token 用量。失败案例优先用于修订工具边界和反馈协议，避免只累积提示词。

### 13.9 单一契约来源与接入方式

集中维护版本化 ToolDefinition：参数 schema、输出 schema、用途说明、前置条件、副作用策略、错误码和示例。由此生成模型工具定义、运行时校验、文档和契约测试骨架；具体断言和实现仍需编写与验证。

```text
结构化工具调用
  → schema、上下文和权限校验
  → Mastra 工具 / 工作流与领域执行服务
  → 调度、浏览器操作、检查与持久化
  → 输出 schema 校验
  → 摘要与证据引用
```

应用内部直接通过模型工具调用机制接入。需要外部 Agent 时增加 MCP 适配层；核心工具契约不绑定传输协议。一次运行固定契约版本，接口变更不静默改变运行中任务的语义。

## 14. 验收场景

下列场景通过正式工具入口在可重置环境验证；故障配置、私有答案和评估器与被测 Agent 隔离。测试任务和生产检查复用执行协议，参见[验证靶场库与持续评估设计](./arena-and-evaluation.md)。

实现后至少验证：

1. 登录一次后，多个只读分支复用会话，恢复条件均被验证。
2. 单账号下购物车写任务串行，快照检查仍可并行。
3. 不同账号修改同一业务资源时仍能识别冲突。
4. 退出登录等待相关分支结束，不破坏其他任务。
5. banner 被关闭前保存证据，恢复成功仍报告原始问题。
6. 按钮改名或移动触发重新定位，错误目标不被缓存为正确映射。
7. 一个规则发现违规不取消兄弟任务；执行错误按显式策略处理。
8. 取消或超时释放可释放资源，副作用未知的资源不被立即复用。
9. 进程崩溃后，根据持久记录核对状态，不盲目重复提交。
10. 漏报反馈可以定位到观察、规则选择、动作或报告阶段。
11. 截图标注与当前视口坐标一致，视觉估计被明确标识。
12. 系统等待时间与模型推理、人工等待等开销分开统计。
13. Agent 不显式调用 checks.run 时，基础动作前后规则和证据仍正常执行。
14. observe 不隐式滚动或关闭浮层，act 不越过当前恢复策略。
15. 过期状态、歧义目标和无效 outcome ID 返回可处理反馈，不执行错误动作。
16. 同一逻辑请求重复投递不会直接重复写操作；结果未知时进入核对流程。
17. spawn 立即返回任务句柄，wait 按游标提供新增事件，不高频重复输出完整日志。
18. 模型填写的权限或副作用字段不能绕过资源准入和父任务预算。
19. 工具 schema、说明、示例和真实返回保持一致，输出不符合契约时记录执行异常。
20. 仅提供目标和入口、没有 Journey 时可以启动探索并逐步记录状态图。
21. 未命中规则时，Agent 仍能登记假设、验证并提交有证据的发现，且不伪造 ruleId。
22. 同一 URL 的弹窗、错误与成功状态可以分别记录，访问记录不误标全面覆盖。
23. 新发现和反驳证据驱动后续计划更新，重复探索受去重和预算约束。
24. 预算耗尽时保留未探索分支与未决假设，不输出全站通过结论。
25. 探索发现沉淀规则或路径前，先区分实际行为与有效业务要求。
26. 框架运行恢复后重建浏览器并验证业务状态，不把工作流快照当作浏览器克隆。
27. Web 连接断开后任务继续，重新订阅可按游标读取持久进度。
28. 暂停、崩溃和重试场景验证实际 runner 的语义，避免重复业务写入。

## 运行记忆与精简观察的实现约束（2026-09-22）

真实模型实验表明，页面信息减少后发生循环，不能直接归因为模型无法理解 a11y。已有实现曾在两次历史压缩中丢失动作参数、结果和假设 ID，使 Agent 无法判断已经执行过什么。保持当前技术栈，先修复工具契约与运行记忆；实验数据见 [浏览器循环实验结果](../plans/browser-loop-experiment-results.md)。

正式执行层使用以下契约：

- 当前状态：a11y、短页面文本、元素引用索引。索引包含 ref、标签、文本、可见/启用状态和阻挡采样数；完整 selector、属性和命中数据通过 `element_details` 按需获取。新观察生成新引用，旧引用不得冒充当前状态。
- 最近历史：最多六轮、默认 8,000 UTF-8 字节，保留完整条目中的工具名、参数、执行状态、短结果文本、错误、假设/问题 ID 和证据引用。不截断结构化参数和标识符；超过预算时移出自动上下文。
- 旧记录：运行内保留完整的语义投影，`historyWindow` 明示已省略的条目数量和索引，`history_read(start,count)` 按需读取。原始工具结果另存运行事件供复盘；该工具不是进程重启后的恢复机制。
- 动作：role/name 按完整名称匹配；多个候选时返回歧义，要求 Agent 明确目标。禁止默认点击第一个候选。
- 新鲜度：结合 a11y、页面文本、元素几何和命中状态判断。相同 a11y 不代表没有遮挡变化；该指纹仍不能代表全部视觉变化。
- 请求统计：失败和中断必须留档；未知 token 用量保持未知。结束时结算未完成的请求，重复回调不能重复记账。

这些约束保证运行过程可继续、可检索、可复盘，并不保证自动发现所有体验问题。当前购物业务提示、结果确认和评估逻辑仍有业务专用部分；多业务通用性和 C0–C5 全量评估需独立验收。
