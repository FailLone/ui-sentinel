# 知识、上下文与未知问题探索

状态：运行上下文、规则、路径、假设、发现及反馈已实现；统一产品知识库、PRD/Figma 接入与探索策略库属于后续设计。

## 知识不止规则

| 类别 | 示例与用途 |
| --- | --- |
| 产品要求 | PRD、设计规范、角色权限、允许失败分支，为“应该怎样”提供依据 |
| 应用地图 | 页面、入口、状态转换，协助规划覆盖范围 |
| 语义映射 | 提交、重试、结果确认与当前组件的对应关系 |
| 路径和场景 | 前置条件、数据、分支、终态、只读或写入权限 |
| 规则和例外 | 已验证检查、参数、适用范围和人工批准的例外 |
| 历史案例 | 确认问题、误报、漏报与修复验证 |
| 探索经验 | 边界采样、恢复方法和常见遗漏，产生新假设 |

事实、产品要求和模型推断必须分开。历史上反复出现的行为不自动成为正确要求；selector 与本次截图坐标是易失观察，不能升级为稳定业务身份。

长期知识应保存来源、修订、适用范围和确认状态；冲突时暴露冲突而非拼接为唯一答案。原始材料保留引用，摘要不替代关键证据。规则是可执行部分，不取代其他知识。

## 当前上下文机制

src/agent/context 组织近期工具回执、业务事实、发现摘要、未决假设与进展。完整工具输出留在持久记录，按引用分页读取；恢复的内容交给下一轮模型。阅读截断、未知 usage 与缺失事实要显式表达。

不把完整页面和全部规则每轮塞进上下文。先提供摘要和候选，需要时展开细节；按事实版本失效缓存。减少 token 不能丢失权限、未决写操作、关键失败或新读取结果。

未来长期检索可按项目、要求版本、页面语义与任务范围过滤，再检索少量候选。先证明实际需求，再决定是否引入全文索引或向量检索，当前不增加 RAG 基础设施。

## R2 方向：Skill 指导工作，工具检索资料，程序记录进度

2026-10-10，用户确认并要求持续保留的实现方向。以下为R2设计约定，不代表已经交付Skill框架或资料路径验证。

R2首批目标为：**网址＋一份文本/Markdown产品说明 → 提取有来源的一条关键路径 → 绑定真实页面并执行 → 需求对照报告。** 资料入口不是阶段终点；正常结果、结果不符、要求含糊及前置条件不足都需有明确结论。先沿用匿名、有界权限，Figma、登录角色、任意业务写入、全PRD覆盖及长期记忆框架后置。

“依据产品资料规划和验证关键路径”适合作为应用内部Skill：说明怎样阅读资料、区分要求与推测、选择路径、调用工具和处理缺口。先由现有主Agent使用随代码维护的版本化说明，不为此增加另一套模型循环或建设完整Skill平台。Skill本身不拥有权限，不决定通过；资料中的产品要求也不必变成全局内置Rule。

Skill应指导Agent按需查询文档，避免每轮重新读完整篇资料。工具负责实际检索，并提供可核对的结果：

| 查询能力 | 返回内容与用途 |
| --- | --- |
| 资料目录 | 已提供的文档、版本、章节和摘要，帮助确定读取范围 |
| 内容搜索 | 关键词命中的原文片段、来源身份及定位；未命中或截断明确说明，不推断要求不存在 |
| 原文读取 | 根据引用位置读取冻结原文及必要上下文，保留精确范围和后续读取位置 |
| 需求与路径查询 | 已提取要求、对应原文、路径步骤及验证状态；必须读取持久记录，不由模型重新编造 |

例如检查筛选器时，可查找资料对“筛选结果”和“重置筛选”的要求，再读取命中段落的上下文。摘要负责定位，最终预期和验证结论引用原文；文档中的链接、代码或指令文本不自动触发抓取、执行或扩大权限。

**文档记忆与执行状态分开。** 前者回答“产品应该怎样”，后者回答“已经执行和验证了什么、还欠什么”。要求及原文引用、前置条件、步骤、实际动作、测量证据、未完成项都应结构化保存，不能只存在于模型上下文。重复查询不能重复执行原动作，也不能把读完资料或生成计划记为验证完成。选定路径之外的资料要求明确列为未检查，不声称整份PRD已覆盖。

首版优先实现目录、关键词搜索和原文定位；资料规模和实际同义词查询问题确有需要后再引入语义检索，不先建设向量库。冻结来源身份、内容摘要及版本；更新资料时，依赖旧版本的要求与路径标记为待重新核对，保留历史运行的原版本和证据，不静默替换。

R2开发和审查以这套分工为依据：Skill负责工作方法，结构化记录负责来源和进度，工具/程序负责读取、执行、测量与证据判断。通用质量标准仍归Rule，与[规则及脚本复用原则](rules-and-rule-library.md#迭代原则规则积累与程序复用)保持一致。

## 未知问题的探索方式

规则负责稳定判断，探索策略负责提醒 Agent 去尝试哪些还未验证的体验。进入新页面、业务成功后、弹窗出现和错误恢复后均可能触发探索；只在路径失败时检查会漏掉成功路径中的问题。

策略设计应包含适用条件、操作预算、假设、反例、证据要求和停止条件。策略缺失不禁止自主探索；执行了策略也不等于该区域所有体验都合格。被跳过的范围及理由要进入报告。

## 已实现案例：视觉输入区域与实际聚焦行为

[视觉发现与聚焦验证](visual-focus.md)已实现这一有界流程，通过 EXECUTION_VISUAL_DISCOVERY 显式开启；它不是通用视觉问题分类器。

1. 根据截图背景、留白、图标和布局推断用户可能认为可输入的区域，同时记录歧义。不能直接把 input 的 DOM 矩形当作视觉预期。
2. 明确真实编辑节点和独立操作区。每个采样点先建立失焦前置条件，再用真实指针点击，并观察焦点/输入响应。
3. 采样中心、两端留白和合理边界，考虑异步聚焦与复合编辑组件。测量失败或范围模糊时保留 unknown。
4. 保存原图、视觉推断区域、实际命中、焦点变化与采样时间；不靠 CSS 属性直接断言体验缺陷。
5. 加入健康反例：容器正确代理聚焦、图标独立操作、合理异步响应、边界含糊、点击前已聚焦。

必须分开验收“提示位置后的定向验证”与“未提示缺陷的自主发现”。已讨论的输入框案例只能用于开发/回归，不能声称是未见案例泛化。未来新增独立交互场景时，同时记录漏报、误报、探索覆盖与成本。

对其他 DOM 可观测问题，Agent 可以通过[可组合调查](composable-investigations.md)提出预期、测量事实并生成程序，不必等待新增专用规则。预期合理性仍需需求依据，正常反例用于识别错误预期和错误绑定。

## 反馈闭环

漏报复盘检查 Agent 是否看见相关状态、是否产生假设、是否选择了有效实验、证据是否被保留、最终如何判定。只加一条规则不能解释它为什么没有去点击输入框留白。

已确认发现可沉淀候选规则；策略、知识和靶场变更同样需要来源与回归。Agent 可以提案，人负责产品预期和发布边界。详见[规则流程](rules-and-rule-library.md)与[靶场职责](arena-and-evaluation.md)。
