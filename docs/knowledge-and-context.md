## 1. 定位与设计原则

Agent 是探索、提出假设和验证问题的主体。知识库提供产品意图、已知事实、可复用路径和历史经验；规则库是其中可直接执行的一部分，不是发现问题的全部边界。

知识库回答四个问题：产品应该怎样、目前观察到了什么、怎样验证，以及哪里仍然不知道。

核心原则：

- 长期知识不整体进入模型上下文；上下文只包含当前任务所需内容。
- 产品要求、实际观察和模型推断分别存储，稳定出现的行为不自动成为正确要求。
- 每条知识有来源、适用范围、修订版本和确认状态。
- 原始资料与原始证据保留引用，摘要不能取代必要的核验依据。
- 未检索到不等于不存在；检索截断、缺失和冲突必须显式表达。
- 规则源码由执行层加载，Agent 默认只读取清单和结果。
- 无相关知识或规则时，允许 Agent 继续提出假设和探索，不能直接判定通过。
- 控制 token 成本不能以静默丢失业务约束、权限或未决副作用为代价。

## 2. 知识内容分类

| 类别 | 内容 | 使用时机 |
| --- | --- | --- |
| 产品要求 | PRD、Figma、设计规范、业务限制及其版本 | 建立预期，确认判定依据 |
| 应用地图 | 功能、页面用途、入口、角色、已知状态及转换 | 规划探索，发现关联入口，减少重复 |
| 路径与场景 | Journey、前置条件、数据要求、分支、终态和验证谓词 | 复用流程，覆盖成功与拒绝等情况 |
| 语义与操作映射 | 业务意图到组件/操作的对应关系，状态识别方法 | 定位动作，验证登录、订单或支付结果 |
| 规则与例外 | 可执行规则、适用范围、参数、确认后的例外 | 稳定执行已知检查 |
| 历史案例 | 确认问题、误报、漏报、复现条件和修复验证 | 提出假设，改进判断和回归覆盖 |
| 探索经验 | 可版本化的探索策略、高价值边界条件、采样方法、常见阻断及恢复策略 | 按状态检索摘要，选中后展开，安排优先级并产生问题线索 |

探索策略的结构、适用条件、预算与发布评估见[探索策略与未知问题发现](./exploration-strategies.md)。策略是本类知识的结构化形态，不是独立于知识库的第二套存储；策略执行记录属于运行状态。

### 2.1 分类示例

- “保存失败后必须保留输入”：产品要求，可进一步实现为规则。
- “订单确认页的主要操作是提交订单”：语义知识。
- “本次提交按钮在右下角”：运行观察。
- “这个 selector 当前匹配提交按钮”：可失效定位缓存。
- “活动开启时曾遮挡失败提示”：历史案例，可触发新的探索假设。
- “关闭活动浮层后再尝试操作”：恢复方法，不表示原始遮挡被认可。

### 2.2 关系模型

知识之间通过显式关系连接，例如：

```text
PRD 要求
  → defines → 预期行为
  → implemented-by → 规则
  → verified-by → 场景
  → applies-to → 功能 / 页面状态

历史发现
  → evidenced-by → 运行证据
  → motivates → 回归场景 / 规则候选

新修订
  → supersedes → 旧修订
```

图关系可以用关系数据库表实现，不要求单独采用图数据库。关联不等于推导已成立；例如“来源是某份 PRD”仍需定位到具体条目和修订。

## 3. 长期知识、运行记录与缓存分离

| 层 | 保存什么 | 生命周期 |
| --- | --- | --- |
| 长期知识 | 有明确来源和范围的要求、语义、路径、规则、案例 | 版本化保存，更新时保留历史 |
| 运行工作状态 | 当前探索图、任务队列、未决假设、进度和副作用状态 | 随运行更新，支持恢复与复盘 |
| 原始证据 | 截图、DOM、测量值、日志、模型输入输出引用 | 按保留策略存储 |
| 加速缓存 | 定位、重复检索和已解析材料 | 可失效、可重建，不作为规范来源 |

运行中发现的地图节点可先作为本次观察保存。提升为可复用应用地图时标注环境、角色和依据，不宣称涵盖所有路径。

被证明有效的观察也可能过期。多次定位成功可以提高复用价值，但不能取消当前状态验证。

## 4. 通用知识模型

```ts
interface KnowledgeRecord {
  id: string;                   // 稳定知识身份
  revision: string;             // 不可变修订
  kind:
    | "requirement" | "app-map" | "journey" | "scenario"
    | "semantic-mapping" | "rule" | "exception"
    | "case" | "exploration-strategy";
  title: string;
  summary: string;
  contentRef: string;

  epistemicKind: "normative" | "observed" | "inferred";
  status: "draft" | "supported" | "confirmed" | "superseded" | "retired";

  scope: {
    projectId: string;
    featureIds?: string[];
    roles?: string[];
    environments?: string[];
    statePredicates?: string[];
  };

  sources: Array<{
    ref: string;
    revision?: string;
    locator?: string;           // 文档条目、设计节点或证据位置
  }>;
  evidenceRefs: string[];
  relations: Array<{ type: string; targetId: string; targetRevision?: string }>;
  validFrom?: string;
  validUntil?: string;
  reviewedAt?: string;
  confirmedBy?: string;
}
```

normative 表示要求，observed 表示实际观察，inferred 表示推断。supported 不等于人工确认，也不表示来源是规范。对推断记录依据和不确定性，不把模型自报置信度当成已校准准确率。

具体知识类型有独立 schema，例如 Journey 的分支、规则 manifest 和例外范围；通用记录是索引与治理外壳，不代替已有执行接口。

## 5. 进入知识库的流程

### 5.1 资料导入

```text
导入 PRD / Figma / 团队约定
  → 保存原始版本与访问范围
  → 按功能和条目解析
  → 提取候选要求、关系和歧义
  → 关联页面、路径、规则
  → 根据依据与确认状态发布可检索修订
```

按语义条目分段，保留标题层级、限定条件和来源位置，避免把例外与正文分离。不能仅依靠固定长度切片表达业务要求。Figma 节点的画面和说明共同作为来源，视觉差异是否违规仍取决于当前有效设计与范围。

### 5.2 从探索中沉淀

```text
运行观察 / 人工反馈
  → 假设与验证
  → 有证据的发现或经验
  → 提出知识候选
  → 明确范围、正反案例和来源
  → 复核 / 测试
  → 发布相应修订
```

发现可以先报告，沉淀不是报告的前置条件。产品约束和扩大影响范围的例外需按既定审阅策略确认；临时语义映射可作为候选复用，但保留状态验证。

并非所有材料都应升级为长期知识。重复日志保留在证据层；偶然位置进入缓存；单次故障可以形成案例，但不直接概括为全局规则。

## 6. 版本、失效与冲突处理

资料更新时创建新修订，通过关系查询找出受影响的规则、路径、映射与案例，标注待复核。不能只新增文本而让旧要求仍默认有效。

检索默认使用当前任务锁定的资料与知识版本。运行中获知重要更新时，显式记录切换或重启决策，不能混用新旧要求后输出一个无版本依据的结论。

有效期、已替代状态和项目例外参与过滤；过期定位缓存直接重建，过期规范仍可供历史复盘读取。

PRD、Figma 和人工决定发生冲突时：

1. 按项目明确配置的权威来源和适用版本判断。
2. 记录冲突双方、范围及证据，不默认最新时间戳一定正确。
3. 无法解决时标记 conflict / unknown，继续不依赖该冲突的工作。
4. 需要新的产品判断时提交待确认项，不能由模型悄悄创造要求。

## 7. 存储与索引

| 存储职责 | 适合保存的内容 |
| --- | --- |
| 关系数据库 | 知识身份和修订、范围、关系、确认状态、规则及路径索引 |
| 全文索引 | 要求描述、案例、操作说明与探索经验 |
| 可选向量索引 | 不同措辞的语义召回 |
| 文件或对象存储 | 原始资料、设计快照、截图、DOM 和执行证据 |
| 独立缓存 | 定位结果、解析结果、检索加速 |

结构化事实使用结构化查询。向量相似度用于找候选，不决定规范优先级、访问权限或最终适用性。权限必须在返回正文和证据前验证，不能仅依赖提示词。

索引跟踪源修订与内容哈希。发布和替代知识时更新索引；索引尚未同步时明确返回状态或回退到主存储，不能静默返回过期规范。

## 8. 按需检索协议

### 8.1 两阶段检索

1. 依据项目、功能、角色、环境、版本和当前状态过滤。
2. 用关键词与可选语义检索召回候选，返回短清单。
3. Agent 或上下文构建器读取选中条目的具体修订。
4. 需要核验时按引用打开原始资料和证据。

严格匹配无结果时，可以在已授权项目内按明确顺序放宽功能或状态条件；不放宽访问权限，也不静默去掉有效版本要求。返回说明本次过滤与放宽范围。

### 8.2 拟定工具

| 工具 | 职责 |
| --- | --- |
| knowledge.search | 返回条目清单、相关性依据、修订、冲突和分页信息 |
| knowledge.read | 按 ID 和修订读取指定条目或章节 |
| knowledge.propose | 提交知识候选或修改建议，复用执行层已定义的提议入口 |

rules.search 是针对规则清单的专门入口，复用知识索引但不将通用检索语义与规则执行混淆。证据读取沿用受权限控制的任务/证据接口。

检索输出至少包含 matchedScope、items、hasMore、nextCursor、truncated 和 warnings。结果设置条数与 token 预算；截断时明确未返回范围。全文缺失、无匹配、权限不可用和索引未就绪分别表达。

### 8.3 重要知识的保证

项目固定约束、当前 Journey 的预期和必要权限信息由结构化依赖直接注入，不依赖 top-k 语义检索碰巧命中。关联条件、例外和必要定义一起读取。

普通案例和经验按相关性选择。没有检索到历史案例，不妨碍 Agent 新建假设；没有充分规范依据，则不能直接断言业务违规。

## 9. 上下文构建器

上下文构建器为当前任务组装有预算的工作包，连接任务状态、知识检索和证据摘要。知识库增长不要求每次模型调用增长。

### 9.1 四层工作记忆

| 层 | 内容 | 加载策略 |
| --- | --- | --- |
| 固定协议 | 工具使用、任务边界、权限和核心约束 | 精简常驻；确定性约束仍由执行层强制 |
| 当前工作包 | 目标、当前状态、步骤、待验证假设、未决副作用 | 按任务更新 |
| 按需知识 | 当前要求、规则清单、相关案例和映射 | 检索后加载 |
| 原始证据 | 截图、DOM、完整日志和文档 | 引用为主，必要时展开 |

```ts
interface WorkPacket {
  taskId: string;
  revision: number;
  goal: string;
  scopeRef: string;
  checkpointRef?: string;
  currentStateRef: string;
  progress: string[];
  openHypothesisRefs: string[];
  unresolvedEffects: Array<{ actionId: string; status: string }>;
  knowledgeRefs: Array<{ id: string; revision: string }>;
  evidenceRefs: string[];
  nextCandidates: string[];
  stopConditions: string[];
  remainingBudget: { actions: number; modelCalls: number; tokens?: number };
  omittedItems: Array<{ ref: string; reason: string }>;
}
```

这是持久工作状态的结构示意。实际给模型的消息由构建器读取必要字段和条目组装，并记录工作包与提示模板版本。

### 9.2 构建流程

```text
读取任务权威状态
  → 确定当前动作/假设需要的信息
  → 加入必须保留的约束与未决状态
  → 检索相关知识并解决版本范围
  → 加入必要证据摘要或图像
  → 按预算去重与裁剪可选内容
  → 校验完整性
  → 生成模型输入
```

预留模型输出和后续工具返回空间，避免把输入填满上下文。图片和工具定义也计入预算估计。具体额度按模型窗口和任务配置，不能把固定条数等同于固定 token 成本。

不能裁掉的内容包括有效权限边界、当前预期依据、未决操作结果、关键冲突和任务停止条件。必要内容仍超预算时拆分任务或分步读取；不能先删掉约束再继续执行。

### 9.3 示例工作包

```text
目标：检查购物车提交订单
状态：活动浮层已出现，提交动作尚未发出
要求：活动内容不得阻挡主要操作（requirement-7@r3）
规则：遮挡、可操作性、价格一致性
案例：关闭浮层后曾发生重复弹出（case-21@r1）
待验证：提交按钮是否被挡；关闭后浮层是否再次出现
证据：snapshot-42
范围：测试购物车；不执行真实付款
```

无关的注册、个人资料和后台知识不进入该工作包。规则源码不进入模型上下文，执行层加载实际脚本。

## 10. 长任务、摘要与并行分支

### 10.1 持久工作状态优先

每个步骤结束或发生重要状态变化时，持久保存完成情况、当前页面和检查点、事实及证据、未决假设、下一步候选、停止条件和副作用状态。

模型对话历史不是唯一状态来源。上下文接近预算、任务切换或进程恢复时，可以基于工作包构建新的模型会话；不要求无限增长同一条聊天记录。

摘要是导航材料，不是新的权威事实。每个关键结论关联来源，版本化保存摘要；摘要与当前执行状态冲突时，以核对后的运行状态为准。

### 10.2 不允许摘要丢失的内容

- 已发出但结果未知的写操作及核对要求。
- 权限、账号资源限制和父任务预算。
- 尚未解决的假设、冲突与未知。
- 当前业务结果的预期依据。
- 检查点是否仍有效、哪些数据已改变。

恢复模型会话不等于恢复页面。执行层必须重新核对浏览器与业务状态，不能按旧摘要盲目点击。

### 10.3 分支上下文

子任务只接收目标、范围、必要知识修订、检查点和证据摘要。父任务读取子任务结果、覆盖变化、未决事项与证据引用，不接收全部原始对话。

分支共享持久知识与探索记录，避免各自重复导入资料；状态更新通过版本和因果引用协调。父任务汇总时保留冲突与 unknown，不能将多个摘要拼成确定结论。

## 11. 检索日志与知识治理

为复盘记录查询、过滤条件、返回的 ID/修订、截断、实际读取条目、最终工作包清单，以及模型引用了哪些依据。敏感正文不因检索日志而重复泄露。

治理任务包括：

- 过期和废弃条目退出默认检索，历史复盘仍可读取。
- 合并重复案例，保留不同环境和触发条件。
- 标注冲突来源，避免相似描述淹没关键约束。
- 按资料变更使派生知识和缓存失效或待复核。
- 保持摘要与原始材料的可追溯关系。
- 按访问权限和保留策略处理证据删除；引用失效明确返回不可用，不伪造原始证据。

## 12. 评估与验收

### 12.1 两类指标

| 维度 | 指标 |
| --- | --- |
| 上下文成本 | 每任务输入量、重复读取量、图像输入量、检索轮数和延迟 |
| 检索有效性 | 必需要求命中、正确版本选择、无关召回、过期/冲突处理和因漏检索造成的漏报 |

成本下降必须结合任务结果和漏报情况评估，不能单独以 token 越少越好。固定案例集应覆盖措辞变化、长文档、相互冲突和缺少资料等场景。

靶场私有答案与保留评估材料不得进入被测知识索引或工作包。测试产生的学习候选隔离保存；用于调优的案例需标记为已见，不能继续作为未见泛化证据。案例发布和数据隔离遵循[靶场库设计](./arena-and-evaluation.md)。

### 12.2 验收场景

1. 购物车任务不加载无关页面的全量知识。
2. 规则脚本在执行层运行，模型仅获取必要清单和结果。
3. 强制要求与相关例外不会被 top-k 检索遗漏。
4. 资料更新后默认检索排除旧要求，历史运行仍能按旧修订复盘。
5. 运行观察不会自动提升为规范。
6. 检索截断、无结果和权限限制有不同返回，Agent 不误判为全部检查完成。
7. 无规则时仍能开展假设验证并报告有证据的发现。
8. 未知提交结果在摘要和新模型会话中保留，避免重复提交。
9. 子任务只加载所需上下文，父任务可按引用展开证据。
10. 必要上下文超预算时拆分工作，不静默丢弃约束。
11. 漏报可追溯到未检索、读错版本、摘要遗漏或后续判断错误。
12. 预算耗尽时报告未探索范围和未决问题，不输出全站通过结论。

## 13. 实施边界

本文确定知识分类、版本治理、检索协议与上下文职责。数据库、全文或向量索引产品、具体分段参数和上下文额度尚未选定，需按资料规模和评估结果确定。

知识提议、读取和检索沿用执行层的工具契约校验、权限控制、结构化返回和审计机制。工具通过 Mastra 接入，领域服务负责知识修订与资源约束。Mastra Memory 可承载会话记忆，但不替代本设计的产品知识库；框架工作流状态与当前工作包通过明确引用关联，不作为同一种数据重复维护。
